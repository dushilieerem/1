## ADR-025: 回测采用单一应用执行管线与可插拔后端

> 状态：已采纳。首期统一单因子回测与因子批量回测；策略回测在下一里程碑迁入同一应用管线。

> 后续决策（2026-08-28）：[ADR-028](../../../docs/05-技术决策/ADR-028-因子回测由BacktestEngine编排四引擎.md)
> 已将因子完整执行入口切换为 BacktestEngine，并保留单一路径、Spec/高层结果及统一调度原则。
> 本文关于 FactorBacktestExecutor 的内容仅是历史基线；策略回测仍不在本次迁移范围。
> 下文的 `factor-backtest-v9` 和数据库清理步骤属于原阶段基线，不适用于 FEAT-030；当前文件缓存为
> `factor-backtest-v11`，新重构明确禁止清理或迁移批量历史。
> 当前因子入口、引擎职责和版本以 ADR-028、ADR-029 及
> `ResearchEngine/docs/02-架构文档/researchengine_architecture.md` 为准；下方“选择”保留原决策的历史依据。

### 问题

当前单因子 API 与因子批量业务都能完成回测，但入口层各自组织配置、过滤、基准、
分层指标和结果投影，导致相同因子和参数可能得到不同结果。批量协调器还曾通过
`FactorBacktestBatchExperiment` 维护一套独立执行封装，回测路径因此随调用来源分叉。

这会直接影响评分卡可比性、缓存命中、历史复现和问题定位。系统需要把“如何计算一次
回测”与“从哪里提交、如何重试、保存什么结果”彻底分开。

### 选择

#### 1. 应用层只有一条回测执行管线

所有因子回测必须经过：

```text
标准化 FactorBacktestSpec
  → 数据版本、股票池和因子解析
  → 因子预处理与交易状态过滤
  → 分组、信号和组合
  → 可插拔回测后端
  → 基准、核心指标、分层指标和预测性指标
  → 标准 FactorBacktestResult
```

HTTP、CLI、Python SDK、单次任务和批量任务只是规格入口或调度方式。缓存、重试、
SQLite、完整 HTTP 响应和 CSV/Parquet 保存属于执行前后的策略，不得复制上述计算步骤。

Native 与 Event 继续作为后端选择，保留 ADR-002、ADR-005 的双引擎决定；“单一路径”
指应用编排和结果契约唯一，不限制后端实现数量。因子首期使用 Native，策略后续通过
同一应用管线接入 Event 或 Native。

#### 2. 统一规格、执行器和结果

- `FactorBacktestSpec` 是不可变规格，包含因子来源及源码哈希、默认参数、日期、股票池、
  基准、组合类型、分组、调仓、成本、过滤、预处理、后端和分析级别。调用来源、任务 ID、
  保存目标和重试次数不进入计算身份。
- （历史阶段）`FactorBacktestExecutor.execute(spec, context)` 是唯一计算入口。它固定读取
  `ResearchDataContext` 的 release，完成因子、行情、股票池、过滤、信号、后端、基准和
  指标计算。
- `start` 之前的历史只用于 rolling 等预热；读取上界严格为 `end/as_of_date`。省略 `end`
  时解析为当前数据 release 的最后可用交易日，并把实际截止日写入标准结果。
- `FactorBacktestResult` 始终包含规格快照、净值、收益、持仓、基准、核心指标、分层/预测性
  结果和溯源信息。`analysis_level` 只控制扩展分析，结果保存目标不改变公式。
- `FactorBacktestExperiment(spec)` 是单因子和批量任务共同提交给 `ExperimentManager` 的
  唯一因子任务类。批量协调器不导入 `FactorExperiment`、NativeEngine、基准加载或指标计算。
- 旧 `FactorExperiment(...)` 构造方式保留为兼容门面，只把旧参数转换为规格并委托执行器，
  继续返回兼容的 `ResultManager`；它不再持有回测算法。

#### 3. 入口、调度、缓存和持久化

- 保留既有因子 API、批量触发/查询接口和响应主结构；API 只做 DTO 映射、任务提交和结果投影，
  不修改 WebApp。
- `FactorBacktestBatchCoordinator` 只负责目录枚举、预检、批次幂等、两槽普通 FIFO、断点续跑、
  一次运行时重试和 SQLite 投影。每个因子提交的都是 `FactorBacktestExperiment(spec)`。
- 同一规格、因子源码和数据 release 必须产生同一标准结果；入口差异只允许出现在任务 ID、耗时、
  缓存状态和持久化状态。
- 统一运行身份为：

```text
spec_hash + factor_source_hash + data_release_id + execution_version + metric_version
```

- （历史阶段）文件缓存升级为 `factor-backtest-v9`，单因子和批量任务共用规格版本和数据版本口径；旧 v8
  缓存自然失效并由 TTL 清理。
- SQLite 使用明确的 schema version 2，批次记录保存 `execution_version`、`data_release_id`
  和 `spec_hash`，因子行保存对应溯源字段；API 以兼容新增字段返回它们。旧数据库不做混写或
  自动迁移。
- 上线时停止服务，解析并确认精确目标路径，直接删除默认数据库及其 `-wal`、`-shm` 文件，
  不创建备份，由应用初始化新的 v2 数据库。发现旧或未知 schema 时运行时失败并提示清理。

### 备选方案

- **保留单因子和批量两套 Experiment**：短期改动小，但继续产生配置、指标、缓存和结果口径漂移，
  否决。
- **让批量协调器直接调用 QuantCore**：可以减少任务对象，但会让批量重新拥有一套计算路径，
  破坏 Manager 的统一边界，否决。
- **把批量策略下沉到 Manager**：会让通用调度器理解业务窗口、重试和持久化，破坏普通 FIFO，否决。
- **立刻统一策略回测**：方向正确但范围过大；先完成因子单次/批量，再迁移策略，降低首期风险。

### 后果

正面影响：相同规格跨入口结果可逐项比较，缓存和批次幂等有共同身份，过滤/基准/指标只维护一份，
历史结果具备数据 release 和版本溯源，后续迁移策略有明确模板。

负面影响：首期需要迁移批量任务和兼容门面，必须清理旧 SQLite 历史；完整结果对象比旧批量标量
摘要更重，批量仍需在协调器线程做状态投影；策略回测在迁移完成前仍保留自己的业务适配器。

### 验收标准

1. 同一 `FactorBacktestSpec` 经单因子和批量入口执行，净值、收益、基准、核心指标、Q1–Q5、
   IC/RankIC/ICIR 一致，排除任务 ID、耗时、缓存和持久化状态。
2. 修改 `end` 之后的行情不影响结果；rolling 因子在 `start` 首日可以使用此前历史预热。
3. 停牌、涨停、去极值和标准化参数在两个入口产生相同因子截面和持仓。
4. 日期、参数、源码、数据 release、执行版本或指标版本任一变化都会使缓存和批次身份失效。
5. 两槽 FIFO、交互任务先到先执行、断点续跑、一次重试、错误分类、HTTP 202/轮询/取消和
   `FactorExperiment` Python 兼容回归全部通过。
