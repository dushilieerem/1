# ADR-026：因子数据库加载与执行器最小改造

- 日期：2026-08-26
- 状态：提议

> 历史设计说明：本文提出的 FactorBacktestExecutor 已由 FEAT-030/ADR-028 删除，
> 当前完整因子流程使用 `BacktestEngine.run()`；因子来源加载目标仍保留，后续设计不得恢复旧执行器。
> 本 ADR 尚未进入当前架构基线；若重新启动，应基于 `app.services.factor`、`app.services.backtest`
> 和 `app.database` 重新设计，不得照搬下文的旧 QuantCore 路径。

## 问题

SVQuant 当前用 `.py` 保存因子实现、用 `index.yaml` 保存目录。这个运行方式本身能够完成因子
计算，但当因子达到数千个后，说明、标签、版本、校验、别名和指标等管理信息分散，检索和追溯
成本很高。

当前 `BacktestEngine` 在 `spec.factor is None` 时通过 FactorEngine 的 loader/resolver 取得
`BaseFactor`，再完成统一的因子回测编排。若未来切换因子存储，变化应局限在 FactorEngine 的
loader 门面和应用层接线，不得重建 `FactorBacktestSpec` 或复制一套回测引擎。

## 选择

1. 用数据库保存因子管理字段和源代码。首期使用应用内仓库接口，数据库可为现有部署的 SQLite；
   后续需要时再替换具体存储，不新增独立 FactorRegistry 服务。
2. 因子以 `(library_name, factor_name)` 作为现有查找键；数据库可以额外保存 `id`、版本、
   标签、校验、指标、别名和依赖等字段，但这些不进入当前 `FactorBacktestSpec`。
3. 在 `FactorEngine` 增加统一的 `load_factor(source=...)` 门面，按 `file/database/code`
   选择注入的 loader；`BacktestEngine` 调用该门面。调整 runner 的接线和 source hash 读取方式。
   `FactorBacktestSpec` 字段、构造、哈希和 `execute(spec, context)` 签名保持不变。
4. 数据库代码加载后必须返回现有 `BaseFactor`。完整 `FactorLibrary` 源码沿用现有类/方法契约；
   方法源码沿用现有模板；FactorEngine 只依赖抽象 loader，不直接写数据库访问逻辑。
5. 继续使用现有 `app.services.factor.tool` 模块。模块级函数就是 Python 中接近 C++ namespace
   静态函数的无状态公共工具，因子通过 `factor_tool.<method>()` 调用，不新增重复工具类。
6. 保留 `factor_code` 自定义入口和旧文件回退开关，直到数据库导入和数值验证完成。

## 备选方案

### 新增 FactorSelector / FactorResolutionService / ResolvedFactor

不采用。它们把一次数据库读取包装成多个运行时对象，改变了现有执行链，却没有解决当前真正的
存储问题。

### 改造 FactorBacktestSpec

不采用。Spec 已经可以携带 `factor_name`、库名、源码哈希和可选的 `BaseFactor`，新增身份对象
会扩大所有单因子、批量、缓存和结果仓库的迁移范围。

### 让 FactorEngine 直接写数据库访问逻辑

不采用。FactorEngine 可以拥有 `load_factor()` 入口，但 SQL、文件系统和代码编译实现通过
loader 注入；这样既统一调用方式，又避免 QuantCore 直接依赖某一种存储。

### 独立 PostgreSQL 注册服务

不采用为本 Feature 的首期方案。服务化、权限、事务、高可用和跨进程部署都可以成为后续 Feature，
当前先用仓库接口隔离实现，避免过早引入运行时网络依赖。

### 继续保存整个 `.py` 文件且 Executor 读取文件

作为迁移回退保留，但不作为主路径。数据库应保存同样的源代码内容，由加载器在内存中编译，才能
真正解除执行器对文件路径的依赖。

## 后果

### 正面

- 因子说明、代码、版本和校验信息可以集中检索和管理。
- 回测执行链几乎不变，`FactorBacktestSpec`、FactorEngine 的计算入口和算法无需迁移；
  Engine 内部已通过 ADR-027 增加兼容式 loader 门面。
- 数据库代码更新可以通过 `code_hash` 自动使缓存失效。
- 旧 `.py + index.yaml` 仍可在迁移期回退，风险可控。
- `factor_tool` 继续复用现有实现，不会产生第二套工具 API。

### 负面

- 需要新增因子仓库、数据库初始化和导入脚本。
- 可信 Python 仍在 ResearchEngine 进程内执行，首期不是安全沙箱。
- 完整库源码中的辅助方法和依赖需要保持原样保存，后续才有机会逐步整理。
- 多实例并发更新、权限和远程数据库不在本 Feature 内，需要后续决策。

## 影响范围

### 保持不变

- `ResearchEngine/app/services/factor/spec.py` 的 `FactorBacktestSpec`。
- `FactorBacktestExecutor.execute(spec, context)` 的公开接口。
- `ResearchEngine/app/services/factor`、FactorEngine 的计算 API 和回测算法（内部 loader
  边界按 ADR-027 整理）。
- 单因子、批量和兼容入口的请求字段。
- WebApp 文件。

### 需要修改或补测

- `ResearchEngine/app/services/factor/engine.py` 的 `load_factor()` 门面和 loader 注入。
- `ResearchEngine/app/services/backtest/engine.py` 的因子解析和 loader 接线。
- `ResearchEngine/app/services/factor/runner.py` 中绕过默认 resolver 的接线。
- `runner._request_factor_source_hash()` 的内置 hash 来源。
- 因子仓库、数据库加载器、导入脚本及其测试。
