# 需求到交付工作流

## 1. 分层

```text
产品战略（L0）
  → 产品能力（L1）
  → Initiative（L2）
  → Feature（L3）
  → 开发任务（L4）
```

宏观层管理 L0-L2，微观层管理 L3-L4。

## 2. 宏观流程

1. 记录战略输入：老板方向、用户反馈、竞品、商业化或技术变化。
2. 输出 Initiative Proposal，说明目标结果、能力影响、成本和风险。
3. 进行战略匹配和 Portfolio 优先级评估。
4. 批准后进入产品路线图，并拆分为 Feature。
5. Feature 交付后，根据结果更新 Backlog、路线图和必要的能力地图。

## 3. 微观流程

1. **Feature Proposal**：判断为什么做、为谁做、MVP 做什么。
2. **Product Requirements**：定义业务流程、边界和可测试的验收标准。
3. **Technical Design**：定义模块影响、接口、数据、测试和回滚方案。
4. **Project Plan**：拆分任务、依赖、复杂度、风险和里程碑。
5. **开发与测试**：仅实现已批准范围；需求变化先回写文档。
6. **Verification**：逐条验证验收标准，记录偏差、限制和遗留项。

## 4. 决策关卡

| 关卡 | 决策 | 通过标准 |
|------|------|----------|
| M1 | Initiative 是否符合战略 | 目标用户、战略价值和成功指标明确 |
| M2 | 是否进入路线图 | 与其他 Initiative 完成优先级和资源比较 |
| G1 | Feature 是否值得做 | 用户问题、MVP 和价值明确 |
| G2 | Feature 做成什么 | 业务规则、边界和验收标准明确 |
| G3 | 是否允许开发 | 满足 Definition of Ready |
| G4 | 是否完成 | 满足 Definition of Done |

## 5. 需求规模裁剪

| 规模 | 判断 | 最少文档 |
|------|------|----------|
| S | Bug 或约 1 人天内的小改动 | 单页 Feature：背景、范围、验收、实现说明 |
| M | 单模块、约 2-5 人天 | Proposal、Requirements、Design/Plan、Verification |
| L | 跨模块、高风险或超过 5 人天 | 完整 Feature 文档包；必要时增加 ADR |
| XL | 新领域、战略项目 | Initiative + 多个完整 Feature 文档包 |

## 6. 宏观影响升级

每份 Feature Proposal 必须声明宏观影响：

- L0：仅内部优化，只更新 Feature。
- L1：既有能力下新增功能，更新 Backlog 和发布状态。
- L2：新增能力或改变模块边界，升级为 Initiative 审查。
- L3：改变用户、市场、商业模式或定位，重新进行战略决策。
