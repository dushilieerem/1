# 服务器市场数据内存运行方案

## 1. 结论

SVQuant 不需要为了减少回测 I/O 而先建设行情数据库。

- **Parquet 是持久化和恢复格式**：保存 `current`、历史版本和日更结果。
- **持久化文件按业务域组织**：同一业务域的相关字段放在一张多字段宽表中。
- **只读内存快照是回测运行格式**：服务器启动时读取一次，后续用户请求只访问内存。
- **数据库不是回测热路径**：即使以后引入数据库，回测节点仍应将选定数据版本加载进内存。

## 2. 当前实现差距

Research API 由 FastAPI 应用持有一个 `DataEngine`。FastAPI lifespan 在开始接收
任务前，只创建活动 release 的 Provider；不预热全部研究字段。`FieldFrameCache` 不设字节
上限、不缓存因子值或任务切片；因子任务按 spec 的日期范围访问字段时，
从共享完整字段按日期和股票池切片并深拷贝到任务私有内存。任务不会重新读取 Parquet，也不能
修改共享快照。

目标不是只优化 `pd.read_parquet`，而是让整个服务生命周期只有一份市场数据对象。

## 3. 目标结构

```text
Parquet current（冷数据，可恢复）
          ↓ 服务启动只读取一次
MarketDataSnapshot（只读内存快照）
├── release_id
├── dates / date_to_position
├── symbols / symbol_to_position
├── numeric_fields: {field -> ndarray[date, symbol]}
├── categorical_fields: {field -> codes + dictionary}
├── index_prices
└── index_weights
          ↓ 预加载完成后 fork
Backtest Worker Pool（共享只读物理内存页）
          ↓
用户 A / B / C 的回测请求只创建计算中间结果
```

## 4. 内存模型

不把全部字段拼成一个巨大三维数组，而是按字段保存：

```python
snapshot.fields["close"]   # 二维只读数组：日期 × 证券
snapshot.fields["volume"]
snapshot.fields["pb"]
```

原因：

- 每个逻辑字段可从所属业务域宽表提取，并在内存中独立访问。
- 数值、布尔、行业和状态字段可以使用不同数据类型。
- 策略只选择需要的字段，字段之间不需要复制。

所有基础数组加载后设置为只读。日期和证券代码只保存一份位置索引。回测请求先把日期和证券转换成整数位置，再从数组中取得视图或最小必要切片。

行业名称、行业代码和状态等字符串字段应在内存中编码为整数 codes，并单独保存字典，不能为每个单元格保留 Python 字符串对象。

## 5. 内存容量估算

数值宽表的基础内存近似为：

```text
交易日数 × 证券数 × 字段数 × 每个数值字节数
```

以 8,758 个日期、约 5,912 只证券、14 个 float64 字段估算，纯数组约 5.4 GiB。加上索引、分类字段、Pandas/NumPy 包装和运行开销，一份完整基础快照应按约 7-10 GiB 预留。

这还不包括每个回测任务产生的因子值、信号、持仓和指标中间结果。因此服务器不能只按基础行情大小配内存，还需要限制并发回测数。

建议：

- 当前十余个日频字段：32 GiB 可做单机验证，64 GiB 更稳妥。
- 后续加入大量基本面和多个并发全市场回测：优先考虑 128 GiB。
- 最终容量以真实快照加载和并发压测为准，不只看 Parquet 文件大小。

## 6. 多进程共享方式

生产服务器建议使用 Linux，采用“父进程先加载，之后 fork 回测 worker”的方式：

1. 主进程加载并冻结 `MarketDataSnapshot`。
2. 加载完成后创建固定大小的回测进程池。
3. Linux 的 copy-on-write 让 worker 共享相同物理内存页。
4. worker 禁止修改基础数组；一旦修改会触发私有副本。
5. API 进程将回测任务投递到进程池，并设置最大并发和排队上限。

不能简单配置多个独立 Uvicorn worker 后让每个 worker 在启动时读取 Parquet；那会形成多份缓存。FastAPI lifespan 发生在 worker 内，也不能天然解决跨进程共享。

Windows 开发环境使用 spawn，不能依赖 fork 的共享效果。Windows 仅用于功能验证；生产内存架构以 Linux 为准。后续如果需要跨机器共享，可再评估 Ray Object Store、Arrow Flight 或独立数据服务。

## 7. 请求流程

```text
收到回测请求
→ 校验 snapshot.release_id
→ 将起止日期和证券池映射为位置
→ 从共享字段数组取得切片
→ 计算因子、信号和回测
→ 释放本次任务的中间结果
```

请求过程不创建持久化 Provider，不调用 `read_parquet`，也不访问行情数据库。

## 8. 数据更新和切换

运行中的快照不可修改。日更流程为：

1. 在磁盘生成新的 Parquet 版本。
2. 启动新的服务实例并一次性加载新快照。
3. 完成字段、日期、证券数量和抽样回测检查。
4. 将新请求切到新实例。
5. 旧实例完成正在运行的回测后退出。

这样不需要在同一进程中同时修改数据，也不会让一个回测同时看到新旧两个版本。代价是滚动切换期间需要容纳新旧两份快照，部署时应预留约两倍基础快照内存，或采用逐节点滚动更新。

## 9. 什么时候需要数据库

以下需求出现时可以增加 ClickHouse 等数据库：

- 多台服务器需要共享持续更新的数据源。
- 需要大量按条件查询、在线图表或跨数据集聚合。
- 分钟/Tick 数据无法合理整体加载。
- 需要实时写入、权限隔离和在线数据服务。

数据库解决数据接入、查询和共享问题，不替代回测节点的内存快照。日频全市场回测仍应从固定版本生成内存数据。

## 10. 实施优先级

### P0：按需字段缓存与任务私有副本（已落地）

- `FieldFrameCache` 持有活动 release 的完整字段，不设 LRU 容量上限。
- FastAPI lifespan 只调用 `DataEngine.load_parquet(...)` 建立活动 release 的 Provider；字段在任务首次请求时才从 Parquet 载入缓存。
- 因子 `BacktestEngine` 使用 `DataEngine.get_task_panels()`；字段首次访问时复制任务所需切片，
  不向共享缓存写入切片或中间结果。
- 策略链路仍在旧面板契约上，待独立回归后迁移到同一任务副本规则。

### P1：多用户并发

- 建立预加载后 fork 的固定回测进程池。
- 限制同时运行的全市场回测数量。
- 测量共享页、单任务峰值、吞吐和排队时间。

### P2：规模增长后再选数据库

- 当多服务器、实时数据或高频数据成为真实需求时再评估数据库。
