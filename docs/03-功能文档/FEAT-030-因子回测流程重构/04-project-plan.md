### M1：基准冻结

- 记录当前工作区、运行依赖、数据 release、因子源码哈希与明确参数，不把隐式默认当基准。
- 复用现有 Data/Factor/Metric、adapter、layered、API/批量及 Python 测试。
- 固定首期收益、展示净值、费用、空组、重复值、缺失值及 core/full 结果。
- 记录本次允许差异与既有缺陷，避免把旧行为修复混入迁移。
- 固定环境记录耗时、读次数和内存，作为 M5 对比证据。

### M2–M3：责任迁移

- 数据源读取/筛选掩码归 DataEngine，因子计算/预处理归 FactorEngine。
- 新 PortfolioEngine 接管分组、权重、持仓及前瞻评价数据准备。
- MetricEngine 收敛收益、净值、IC、分组和扩展计算；公共旧指标接口保持。
- 每个阶段先完成小样本和边界测试，再接入完整链路。
- 公共函数迁移需考虑策略消费者，不能全仓删除旧 backtest 包。

### M4：统一接线

- 单次、批量和 Python Experiment 委托同一 BacktestEngine，计算不进入 Manager 或协调器。
- 四项可选参数默认关闭，批量解除强制过滤并开放对应 API/CLI 参数。
- 诊断贯通当次结果/缓存/日志；不更改批量历史表或错误字段语义。
- execution=v3、cache=v10 统一来源；批次键及断点续跑包含新执行身份。
- 保存与绘图置于计算后，保持输出行为；只清理已经迁移的因子专属旧调用。

### M5：验收交付

- 逐项执行 AC-01–AC-12，保存数值对比、失败定位和已审核差异。
- 核心公共能力涉及多个服务，最终运行 svquant 环境全量测试。
- 核验无 WebApp、因子数据库、策略模式及历史 schema 的越界改动。
- 提交前运行 GitNexus detect_changes，确认只影响预期符号与流程。
- 完成后才更新“当前实现”、新版本元信息及 Feature 交付状态。

## 6. 发布与回滚

1. 全量回归及验收通过，保存代码/配置版本和数据 release 标识。
2. 停止接收新任务，等待在途任务结束，再切换新版本并恢复接收。
3. 新执行/缓存/批次身份隔离旧结果；不迁移 schema、不删除历史或数据库文件。
4. 验证单次提交/轮询、批量两槽、默认开关、显式过滤、告警与缓存命中。
5. 出现未预期数值或接口回归时，部署上一已验收版本；保留原数据与未提交改动。
6. 回滚不通过重置用户工作区实现，不执行旧 ADR 中其他阶段的数据库清理指令。
