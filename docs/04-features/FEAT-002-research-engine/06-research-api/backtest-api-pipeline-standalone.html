Panel、懒加载和缓存：self.close 到底是不是每次读盘

Panel 是项目自定义容器，不是 pandas.Panel

① Panel 层缓存

同一个 Panel 重复访问 self.close，命中 Panel._cache，返回同一个字段视图。

② _LazyPanels 视图缓存

以 (field, symbol_key) 缓存字段视图。panel 和 factor_panel 有独立 Panel 缓存，但共享底层懒加载映射。

③ 进程 FieldFrameCache

按发布版本、字段、日期和股票列缓存原始字段/视图；物理 Parquet 字段也有进程级缓存。

self.close / self.openFactorLibrary 属性访问
→
Panel._get按字段缓存当前 Panel 视图
→
_LazyPanels.get_view按字段 + 股票池复用底层视图
→
FieldFrameCache / Parquet缓存命中或首次物理读取
关键边界：数据读取完毕时只调用了 calculation_panels.get("close")。如果因子之后第一次访问 open、volume 或其他字段，懒加载会发生在“数据读取完毕”之后。当前 Provider 对合并 Parquet 先读取逻辑字段的全部列，再做股票池列重排。

为什么 Alpha158 beta 在全 A 特别慢

这是当前实现的计算形态，不是新的性能基准

看起来像 rolling，实际是逐窗口 Python 回调

_rolling_apply(frame, window, _linear_slope) 调用 frame.rolling(...).apply(func, raw=True)；每个窗口都会进入 Python 函数。

窗口内部又调用 np.polyfit

_linear_slope 每次执行 np.polyfit(np.arange(len(values)), values, 1)[0]，不是一次矩阵级斜率计算。

股票数直接放大回调次数

当前全 A 约 5916 只 × 2335 个交易日，单个 beta 因子约 1380 万个窗口回调；CSI300 约 70 万个，数量级差异与耗时差异一致。

不要混淆两类操作：self.close + self.open、self.close.pct_change(20) 主要由 pandas/NumPy 对宽表执行；rolling.apply(Python callback) 则会退化为大量窗口级 Python 调用。当前页面只记录这个事实，不预先规定后续优化方案。

当前实现中的契约差异

只记录，不在本次页面更新中修复

过滤参数尚未进入单因子执行

filter_limit_up / filter_suspended 会返回到 meta，但单因子配置没有打开 factor_batch.filters_enabled。

stamp_tax 尚未传给 BacktestConfig

请求值写入了配置，但 FactorExperiment.run 构造 Native 回测配置时没有传入印花税字段。

后台错误在任务层呈现

提交阶段可能返回 422/429/503；执行阶段通过轮询看到顶层 status=failed 和 error。

批量边界：每日全量批次不放进这张单因子 API 主图。它后续应复用这里的 FactorExperiment 核心链，业务差异只在全库枚举、双槽并发、重试、批次状态和结果入库。
