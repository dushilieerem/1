# Product Requirements：因子批量回测与指标仓库

## 用户故事

1. 作为任务计划或研究员，我希望显式传入 `as_of_date`，执行一个确定的交易日批次。
2. 作为研究员，我希望批次包含索引中的每个内置因子，并能区分成功、失败和跳过。
3. 作为研究员，我希望每个成功因子都有六行分组指标和 IC 汇总，并能按日期查看历史。
4. 作为运维人员，我希望任务中断后重跑可以续跑，重复触发不会制造重复批次。
5. 作为系统使用者，我希望交互式回测不会被批量任务插队；批量任务最多只占用自己的两个未完成窗口。
6. 作为调用方，我希望提交接口立即返回任务 ID，并能轮询到批次 ID 和最终结果。

## 固定业务配置

| 项目 | 要求 |
|---|---|
| 数据目录 | `MarketData/current`；不记录数据指纹 |
| 区间 | `as_of_date - 10 年` 至 `as_of_date`，允许短历史 |
| 股票池/基准 | `CSI_ALL` / `CSI300` |
| 组合 | 纯多头、5 组、每日调仓、core |
| 过滤/成本 | 涨停和停牌过滤配置开启，沿用现有默认交易成本 |
| 保留 | 仅标量指标和状态长期保留 |

## 业务流程

1. 读取并校验索引，计算目录版本；索引或基础行情预检失败时批次为 `failed`。
   `as_of_date` 必须出现在当前 CSI300 交易日序列中。
2. 校验全 A 股票池、CSI300 基准和评估窗口。
3. 创建或复用批次；协调器向唯一 Manager 提交最多两个批量因子，Manager 内部保持普通 FIFO。
4. 每完成一个任务立即写入因子状态与指标，再补充一个任务；不预先提交第三个批量因子。
5. 如果交互任务先于补充动作进入 Manager 队列，普通 FIFO 保证交互任务先执行。
6. 因子运行时异常自动重试一次；缺数据、参数错误和不兼容因子不重试。
7. 所有因子进入终态后更新批次计数并标记 `completed`。
8. 协调线程完成后，任务状态标记为 `succeeded` 或 `failed`；`dry_run` 不创建持久化批次。

## 异常行为

- 单库加载错误仅影响该库登记的因子行；其他库继续执行。
- 空净值、缺少必要字段或无法形成分组结果标记 `skipped`。
- 最终运行异常标记 `failed`，保留最后一次错误码和错误消息。
- 历史不足但有有效结果标记 `succeeded` + `short_history`。
- HTTP 查询只读；不存在的批次返回 404。

## 验收标准

- 动态索引中的每个登记因子恰好进入 `succeeded`、`failed` 或 `skipped`。
- 每个成功因子有 Q1、Q2、Q3、Q4、Q5、benchmark 六行分组指标和一行预测性指标。
- 相同批次键重复运行不新增记录，`--force-retry` 新建批次并关联旧批次。
- 相同非 `force_retry` 请求在进程内复用任务 ID，`force_retry` 创建新任务；提交接口返回 `202`。
- 任务查询能在批次创建后返回 `batch_id`、`batch_url` 和结果，任务快照保留 60 秒。
- 进程中断后重新运行只继续未完成因子。
- 任意时刻批量业务提交给 Manager 的未完成因子不超过 2 个；一个进入终态后才出现下一个提交。
- 交互式任务若已先进入 Manager 队列，不会被后提交的批量因子插队。
- 数据库不产生曲线文件、每日 IC 文件或其他大序列。
