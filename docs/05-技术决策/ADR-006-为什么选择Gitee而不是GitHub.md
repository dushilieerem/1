# ADR-006：为什么选择 Gitee 而不是 GitHub

- 日期：2026-07-21
- 状态：已接受
- 关联：`../00-文档治理/需求到交付工作流.md`、`../01-需求文档/项目组合/portfolio-backlog.md`

## 管理层摘要

SVQuant 是**闭源商业项目**，其核心代码、量化研究方法、数据处理逻辑、策略参数和未来客户资产均属于重要商业资产。本决策选择 Gitee 作为当前私有主仓，核心目标是在国内团队协作稳定性的前提下，以可控的权限和审计流程保护这些资产。

| 关注点 | 结论 |
|---------|------|
| 为什么做 | 为闭源代码和研发资料确定唯一、受控的协作入口，避免资产分散和权限失管。 |
| 不做的影响 | 代码可能散落在个人仓库或多平台，离职交接、权限回收、审计和泄露追溯难度上升。 |
| 为什么现在做 | 项目已进入实质开发，越晚统一仓库、权限和分支规则，迁移与治理成本越高。 |
| 资源投入 | 使用托管私有仓库；需指定 1 名仓库管理员，并执行成员权限、密钥和备份的例行检查。 |
| 预计收益 | 保障核心研发资产可控，降低日常协作阻塞，并为后续客户数据、策略和生产系统治理打下基础。 |
| 主要风险 | 账号被盗、权限过宽、密钥或数据误提交、平台服务中断。通过本 ADR 的安全基线和定期复核缓解。 |
| 下一步 | 配置私有仓库、最小权限、受保护分支和双因素认证；建立离职回收、备份与安全事件响应流程。 |

> 安全结论：Gitee 与 GitHub 都能承载私有仓库；平台名称本身并不自动决定安全性。SVQuant 选择 Gitee 是出于当前国内闭源团队的协作可达性和治理成本考虑，实际安全性由私有化配置、权限管理、代码审查、密钥治理和备份恢复能力共同决定。

## 问题

SVQuant 需要确定代码托管与协作平台。项目当前以国内团队和 A 股量化投研场景为主，且以闭源方式开发和商业化；日常协作需要稳定完成代码浏览、拉取、推送、Issue、Pull Request、权限审计和成员交接。

GitHub 拥有更大的全球开源生态，但在当前阶段，协作平台首先应降低国内团队的日常访问与使用成本，并保障私有研发资产可控，而不是优先追求海外曝光。因此需要明确为什么私有主仓选择 Gitee，而非 GitHub。

## 选择

将 **Gitee 私有仓库作为 SVQuant 当前唯一的主代码仓库与协作平台**。未经管理层批准，不得将完整源代码、策略、配置、数据样本或内部文档镜像至公开平台。

具体约定如下：

- 日常开发、分支管理、代码评审和 Pull Request 均在 Gitee 完成。
- 贡献者按 `Fork → Feat_xxx 特性分支 → 提交 → Pull Request` 的流程协作。
- 代码、产品与技术文档继续与主仓一同版本化，避免决策和实现脱节。
- 对外开源、GitHub 镜像或向第三方授予仓库访问权，必须经过管理层与技术负责人审批，并完成代码、密钥、数据和文档的脱敏审查。
- 当产品进入需要海外开发者、国际开源社区或全球生态集成的阶段时，评估建立仅含获批开源组件的 GitHub 仓库；不得默认镜像闭源主仓。该调整需另行记录 ADR。

### 闭源仓库安全基线

1. **仓库与访问**：所有业务仓库必须设为私有；按最小权限分配访问权，普通开发者不授予管理员权限；成员角色和仓库访问权限至少每季度复核一次。
2. **身份与凭据**：管理员和可写成员启用双因素认证，使用个人账号和独立 SSH 密钥或访问令牌；禁止共享账号、共享令牌和长期未轮换的凭据。
3. **分支与发布**：`main` / 发布分支启用保护规则，禁止直接推送；合并必须经过至少一名非提交者评审，并保持构建或测试通过。
4. **敏感信息**：严禁提交生产密码、API Key、券商凭据、客户数据、未经授权的行情数据和私有策略参数；敏感配置仅以示例文件入库，真实值使用受控的密钥管理方式保存。
5. **审计与交接**：保留成员、权限、PR 和发布记录；人员转岗或离职时，当日回收仓库权限、令牌和部署密钥。
6. **备份与恢复**：定期制作加密的 Git 镜像备份，并至少每半年验证一次可恢复性；备份访问权限与主仓分离管理。
7. **供应商与事件**：采购或升级托管服务前，评估其私有仓库、访问控制、审计、备份、数据处理和事件通知能力；发生疑似泄露时立即撤销相关凭据、冻结访问、保全记录并完成影响评估。

## 备选方案

### GitHub 作为唯一主仓

暂不采用。GitHub 的全球开发者生态、开源传播和第三方集成优势明显，适合面向国际社区的项目；但对当前以国内成员为主的闭源团队而言，日常网络可达性和访问体验存在不确定性，会放大协作等待、成员接入和运维沟通成本。GitHub 私有仓库并非不能满足安全需要，但其生态收益尚不足以抵消当前协作成本。

### Gitee 与 GitHub 双主同步

暂不采用。双主需要处理镜像延迟、分支保护与权限一致性、Issue/PR 状态分散及发布来源唯一性等问题；对闭源项目还会新增代码误公开、权限不一致和密钥泄露的攻击面。0-1 阶段团队规模和外部贡献尚不足以抵消这部分维护成本。若后续需要 GitHub 曝光，仅发布经过审批的独立开源组件，并明确 Gitee 为闭源代码的唯一事实来源。

### 自建 GitLab 或其他代码托管服务

暂不采用。自建方案可获得更高的权限与数据控制，但需自行承担部署、高可用、备份、升级、安全修复及日常运维。当前产品核心投入应放在量化投研能力，而不是代码托管基础设施。

## 后果

### 正面影响

- 国内团队可用更稳定、低门槛的协作入口完成日常研发，缩短新成员接入和代码评审的等待时间。
- 平台的中文界面、中文社区和本地化服务更贴合当前团队的沟通与协作习惯。
- 托管服务替代自建运维，使 0-1 阶段资源聚焦于数据、研究、回测和 AI 能力建设。
- 通过私有仓库、最小权限、受保护分支和审计记录，将核心代码与量化研究资产纳入可追溯的访问控制范围。

### 负面影响与缓解

- 国际开源曝光和海外贡献者触达弱于 GitHub。缓解方式是在形成稳定、可公开的 SDK 或开源组件后建立独立 GitHub 仓库，并维护英文 README。
- 部分全球化开发者工具和开源项目默认围绕 GitHub 组织。缓解方式是优先使用与 Git 协议兼容的通用工作流，避免把构建、发布或自动化强绑定到单一平台私有能力。
- 若未来双平台并存，可能出现提交、Issue 和 PR 分散。缓解方式是预先指定唯一事实来源，并只在主仓进行评审、发布与版本标记。
- 托管服务、账号或配置失误仍可能导致代码泄露或不可用。缓解方式是执行安全基线、定期权限审计、加密备份和恢复演练；不得将平台选择误认为安全治理的替代品。

## 复审条件

出现以下任一情况时复审本决策：

1. SVQuant 开始公开招募海外贡献者，或国际社区成为重要获客渠道；
2. 需要深度使用仅在 GitHub 生态中成熟可用的开源协作能力；
3. 团队形成稳定的双平台同步、权限治理与发布流程；
4. 国内团队的日常协作稳定性不再是选型差异。
5. 闭源商业化对审计、合规、客户隔离或私有部署提出新的强制要求。
