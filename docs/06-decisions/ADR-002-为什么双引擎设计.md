# ADR-002: 为什么采用双引擎设计（向量化 + 事件驱动）

> **决策记录**：Architecture Decision Record
> **日期**：2026-07-15
> **状态**：已实施
> **关联**：`ADR-001-为什么使用向量化回测.md`、`../05-architecture/system_architecture.md` §3

---

## 背景

量化回测面临两种差异巨大的计算模式，行业中有三种架构选择：

1. **纯事件驱动**（聚宽、米筐、QuantConnect）
2. **纯向量化**（部分自研方案）
3. **双引擎**（我们的选择）

## 决策

**采用"向量化 + 事件驱动"双引擎架构，通过适配层统一接入。用户根据场景选择，因子代码零改动。**

---

## 为什么不做纯事件驱动？

| 问题 | 说明 |
|------|------|
| **性能瓶颈** | 5000 标的 × 3 年日线 = 360 万 bar，逐 bar 推进开销巨大 |
| **因子计算不适合** | IC/IR/分层分析本质是矩阵运算，事件驱动强行适配增加复杂度 |
| **快速迭代受阻** | 改一行因子逻辑需要完整跑一遍事件循环，开发效率低 |

聚宽/米筐选择纯事件驱动，是因为他们的目标用户需要精确模拟。但对 SVQuant 的早期用户（因子研究者）来说，向量化更快更合适。

## 为什么不做纯向量化？

| 问题 | 说明 |
|------|------|
| **无法精确模拟 A 股规则** | T+1、涨跌停、条件单本质是时序逻辑，向量化只能近似 |
| **复杂策略表达能力有限** | 止损、追涨、择时等策略难以用矩阵运算表达 |
| **与实盘差距大** | 向量化回测结果与实盘差异大，降低可信度 |

---

## 双引擎的挑战与应对

| 挑战 | 应对 |
|------|------|
| **策略代码需要适配两种引擎** | 统一 `IStrategy` 契约，信号格式标准化为"日期×标的"权重矩阵 |
| **两套代码维护成本** | 通过 `IBacktestEngine` 接口抽象，后端实现隔离 |
| **结果一致性** | 相同输入，两种引擎的输出差异在可接受范围内（≤ 5%） |
| **用户困惑选哪个** | 默认使用向量化；当用户需要精确模拟时自动提示切换到事件驱动 |

---

## 适配层：双引擎的关键设计

```
ResearchEngine（因子代码不变）
       │
       ▼
IBacktestEngine.run(signals, config) → BacktestResult
       │
  ┌────┴────────────┐
  │                  │
VectorBTEngine   NativeEngine
(wraps vectorbt)  (自研)
```

### 六个领域接口

| 接口 | 向量化后端 | 事件驱动后端 |
|------|-----------|------------|
| IStrategy | ✅ 共享 | ✅ 共享 |
| IDataFeed | ✅ 共享 | ✅ 共享 |
| ICalendar | ✅ 共享 | ✅ 共享 |
| IPortfolio | 内化 | 可插拔 |
| IExecution | 内化 | 可插拔 |
| IMetrics | ✅ 共享 | ✅ 共享 |

**关键洞察**：向量化后端把组合管理和撮合逻辑"内化"在引擎内部（因为向量化无法外部注入时序逻辑），事件驱动后端则暴露为可插拔组件。

---

## 给老板的解释

**双引擎好比汽车的"经济模式"和"运动模式"：**

- **经济模式（向量化）**：日常通勤用，省油（快），够用
- **运动模式（事件驱动）**：跑山路过弯用，费油（慢）但精确

**为什么两个都要？**
只做经济模式，用户跑山路会翻车（复杂策略不准确）；只做运动模式，日常通勤太费油（慢）。两个模式通过一个"驾驶模式旋钮"（适配层）切换，发动机（因子代码）不用换。

**竞争对手怎么做？**
聚宽和米筐只有"运动模式"（事件驱动），所以用户每次回测都等很久。BigQuant 只有"经济模式"（图形化），所以复杂策略跑不了。我们两个都有，用户自己选。
