# ADR-008：为什么采用框架无关的预测模型接口

- 日期：2026-07-22
- 状态：提议
- 关联：FEAT-010、FEAT-003、ADR-001、ADR-005

## 问题

SVQuant 需要调用算法组以不同机器学习和深度学习框架开发的预测模型，并将模型输出用于因子分析和策略回测。若模型直接操作回测引擎或把某一个训练框架写入 QuantCore，平台会面临框架依赖冲突、数据时点不透明、交易口径分散和核心包膨胀的问题。

## 选择

采用框架无关的 `BasePredictiveModel` 插件契约：模型接收平台构造的、带可得时间的训练/验证数据集，并仅返回带 `(date, instrument)` 索引的样本外预测分数。ResearchEngine 负责模型运行、切片、校验和运行清单；QuantCore 保持数据、因子、指标、组合与回测的通用内核。预测分数被标准化为因子面板，再复用现有指标和向量化回测路径。

核心依赖仅限 Pandas/NumPy；PyTorch、TensorFlow、sklearn 等由具体模型以可选依赖管理。MVP 使用受信任的内部 Python 模型；隔离执行、GPU 调度、模型注册和在线推理留给后续 Feature。

## 备选方案

### 绑定单一框架（例如仅支持 PyTorch 或 Qlib）

不采用。虽然首个模型接入更快，但会限制算法组选型，把训练框架生命周期和依赖带入平台核心，后续迁移成本高。Qlib 的数据和模型体系可作为参考实现，而不是 SVQuant 的强制运行时。

### 允许模型直接返回订单或调用回测引擎

不采用。这样会使交易成本、市场规则、调仓时序和审计逻辑散落在模型中，无法公平比较模型或复用双引擎架构。模型应只提供预测，策略和执行由平台统一管理。

### 先建设模型仓库、容器平台和 AutoML

不采用。它们对生产化很重要，但当前尚未验证第一个模型的研究闭环；过早引入会显著扩大交付、运维和安全范围。

## 后果

### 正面

- 算法组可使用不同框架开发模型，而平台保持稳定的接入与回测口径。
- 数据可得性、训练/测试隔离和预测索引由平台集中审计，降低未来函数风险。
- 模型预测能同时走因子分析和策略回测，无需维护两套模型输出接口。
- 未来可在不改变模型语义的前提下，把运行器迁移至独立进程、容器或 GPU 队列。

### 负面与约束

- 算法组必须遵守长表输入和预测索引契约，并为每种框架维护轻量适配代码。
- MVP 的内部 Python 插件不是安全沙箱，不能直接开放给不受信任的外部用户代码。
- 初期仅支持日频、批量预测和向量化回测；事件驱动或在线模型须通过新的设计与验证。
