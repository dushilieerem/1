# ADR-010：为什么采用统一数据引擎和多数据源适配

- 日期：2026-07-24
- 状态：已接受
- 关联：FEAT-001、FEAT-010、ADR-003、ADR-008

## 问题

SVQuant 需要同时面对 Wind、AkShare、iFind、CSV、ClickHouse 等来源。它们在证券代码、字段名、单位、复权口径、可查询频率、数据许可和可得时间上均不相同。若因子、回测或 API 直接调用各供应商 SDK，会导致：

- 研究代码绑定供应商字段名，切换或增加数据源时需要修改因子与回测逻辑；
- 同名字段可能有不同单位、复权或财务口径，结果不可比较且难以审计；
- 历史回测依赖在线请求，受网络、额度、供应商修订和会话状态影响，无法稳定复现；
- 每个业务模块各自维护下载、缓存和异常处理，数据质量规则分散。

## 选择

采用 `IDataProvider → DataEngine → Panel` 的统一访问链路：

```text
供应商 SDK / 文件 / 数据库
        ↓ 供应商适配器（WindProvider、AkShareProvider、iFindProvider 等）
IDataProvider：统一的 bars / panels / index / universe 契约
        ↓
DataEngine：选择 Provider、向上层隐藏来源差异
        ↓
Panel：标准字段的 日期 × 标的 数据面板
        ↓
FactorEngine / ResearchEngine / Backtest
```

### 1. 历史数据与在线数据分层

- **历史回测和批量研究**：由 `MarketData/DataIngestion` 通过授权数据源批量采集、校验并发布版本化 Parquet；`FieldParquetProvider` 从 `MarketData/current` 读取已发布的标准字段。数据清单、字段字典和哈希共同定义可复现输入。
- **实时、盘中或临时查询**：使用 `WindProvider`、未来的 `iFindProvider` 或其他在线适配器直接访问供应商。在线结果不得自动混入已发布历史面板；如需用于后续回测，必须经采集流程校验并形成新的数据版本。

`FieldParquetProvider` 不是另一套数据语义，而是历史标准数据的高效读取实现：按字段扫描、懒加载 Parquet，并在 API 进程生命周期内缓存已访问面板。

### 2. 标准字段优先于供应商字段

因子和策略只能使用字段字典中的标准名，例如 `close`、`amount`、`total_mv`、`net_profit_ttm`，不得使用 `amt`、`mkt_cap_ard` 等供应商字段名。每个供应商适配或采集任务维护显式映射：

| 标准字段 | Wind 示例 | AkShare 示例 | iFind 示例 |
|---|---|---|---|
| `amount` | `amt` | `成交额` | 由 iFind 适配器声明 |
| `total_mv` | `mkt_cap_ard` | 不作为主历史来源 | 由 iFind 适配器声明 |
| `pb` | `pb_lf` | 需明确来源和口径 | 由 iFind 适配器声明 |
| `adj_factor` | `adjfactor` | 不以隐式复权价格替代 | 由 iFind 适配器声明 |

映射必须同时声明单位换算、复权选项、报告期/公告日规则、来源版本和缺失值语义。无法等价映射的字段不进入标准字典，而以新字段和明确口径另行评审。

### 3. 多数据源整合规则

1. **不静默拼接**：同一标准字段、同一日期和证券的多个来源不能按“谁有值用谁”混合。每个发布版本必须记录该字段的唯一主来源；补源、切源或修订生成新版本。
2. **标准化后再整合**：先统一证券代码、交易日、单位、币种、复权口径和可得时间，再允许写入同一版本；原始字段和值始终保留来源与版本。
3. **历史财务以公告日为准**：财务数据先保存原始披露记录，按公告日生成点时面板；不能用供应商提供的“最新历史值”回填过去。
4. **冲突可审计**：发现来源冲突时，质量报告记录差异、阈值、处理决定和责任人；未经确认的冲突使字段状态保持 `blocked`，不对因子引擎伪造可用值。
5. **能力按 Provider 声明**：Provider 应明确支持的市场、频率、字段和时间范围。调用不支持字段时返回明确缺字段异常，而不是改用其他来源或用零值填充。

### 4. Provider 的实现要求

- 新数据源实现 `IDataProvider`，并在 Provider 内完成供应商代码、请求参数和结果格式转换；上层不感知 SDK。
- Provider 返回的字段名、索引、证券代码和错误语义必须符合标准契约；必要时只实现其实际支持的接口，不用伪造完整能力。
- `DataEngine` 负责持有和替换 Provider；API 服务中按“每个进程、每个数据版本”复用 `DataEngine` 与 `FieldParquetProvider`，按字段懒加载，不能无差别加载所有历史数据。
- 实时 Provider 必须考虑供应商登录、并发、限流和超时；这些运行时限制不能泄漏为因子公式或回测逻辑。

## 备选方案

### 让因子和回测直接调用 Wind、AkShare、iFind SDK

不采用。实现初期看似直接，但会把供应商差异和授权依赖扩散到研究代码，历史结果也无法稳定复现。

### 只选择一个供应商并取消适配层

不采用。Wind 可作为当前主历史来源，但产品需要保留用户导入、免费开发数据源、实时数据源和未来企业数据源的接入能力。单一供应商不应成为 QuantCore 的架构边界。

### 每个数据源各自维护一份专用因子和回测逻辑

不采用。这会造成指标口径分叉，难以比较策略，也使 AI 生成的研究代码无法跨部署运行。

### 在线数据直接写入当前历史目录

不采用。在线查询没有经过完整质量和版本校验，直接覆盖会破坏历史回测的可重复性。必须先进入采集发布流程。

## 后果

### 正面

- 因子、策略和回测保持供应商无关，新增 AkShare、iFind 或数据库适配器不改变研究接口。
- 历史数据版本化、字段语义和来源可追溯，减少未来函数和供应商修订带来的不可复现风险。
- `FieldParquetProvider` 将主要研究负载限制在所需字段，适合 API 服务的进程级缓存与多 worker 部署。
- 实时与历史工作负载各自使用适合的通道，不以在线稳定性牺牲回测可信度。

### 负面与约束

- 每个新 Provider 都需要维护字段映射、能力声明和契约测试，不能仅包一层 SDK 调用。
- 同一概念跨供应商可能不能完全等价；当口径不同，应保留为不同标准字段或明确版本切换。
- 统一接口不代表所有 Provider 都支持所有字段或频率；调用方必须处理明确的“不支持”错误。
- 数据授权仍由具体供应商合同决定；统一访问层不授予缓存、展示或再分发权限。
