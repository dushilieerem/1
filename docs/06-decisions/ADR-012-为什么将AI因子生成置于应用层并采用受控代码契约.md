# ADR-012：为什么将 AI 因子生成置于应用层并采用受控代码契约

- 日期：2026-07-27
- 状态：提议

## 问题

Web 用户需要以自然语言生成可回测因子。现有 `ResearchEngine` 是无状态研究计算服务，能够接收并执行因子函数源码，但不负责用户身份、供应商密钥、用量、因子资产或 Web 交互。若直接在回测服务中接入 LLM 并执行原始模型输出，会混淆职责并放大任意代码执行和密钥泄露风险。

## 选择

在 SaaS 应用层建立 AI Research Service：由它持有第三方 LLM 密钥、能力目录、提示词、限流、幂等与审计；它只返回经 JSON Schema、AST 和编译校验的单个 `FactorLibrary` 方法草稿。用户审阅确认后，Web 将该函数按既有 `factor_code` / `factor_name` 契约提交给 `ResearchEngine` 回测。

生产回测执行须使用受限子进程或容器；静态校验不作为执行隔离的替代品。

首期 Provider 固定为字节火山方舟 AgentPlan API（Base URL 由服务端配置），模型别名为 `ark-code-latest`。真实 API Key 只保存在密钥管理服务或部署环境变量中，绝不进入仓库、文档或浏览器。

## 备选方案

1. **在浏览器直接调用第三方 LLM**：实现快，但会暴露密钥、无法统一审计/配额，也无法保证提示词和模型版本。
2. **在 ResearchEngine 内调用 LLM 并自动回测**：调用链短，但破坏无状态计算边界，使密钥、用户治理和任意代码风险进入核心回测服务。
3. **允许 LLM 输出任意 Python 后立即执行**：表达力高，但无法建立可靠的审查与安全边界，不适合面向 Web 用户开放。
4. **只输出 DSL，不输出 Python**：安全性更高，但现阶段需要新建 DSL 与编译器，且不能复用已存在的因子回测函数契约；可作为后续演进方向。

## 后果

- 正面：保持 ResearchEngine 和 QuantCore 的职责稳定；密钥与调用治理集中；生成结果可读、可编辑、可追溯，能立即复用现有回测 API。
- 负面：需要额外的 AI 服务、存储、限流和安全运维；受控 AST 子集会限制首次可生成的复杂度；第三方模型输出存在不确定性。
- 演进：当字段、工具与安全需求稳定后，可将受控 Python 子集逐步收敛为因子 DSL，同时保留现有函数接口作为兼容层。
