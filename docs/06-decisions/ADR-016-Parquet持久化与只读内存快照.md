# ADR-016：Parquet 持久化与只读内存快照

- 日期：2026-08-11
- 状态：已接受
- 关联：FEAT-024、ADR-003、ADR-010、ADR-017

## 问题

多用户提交回测时，如果每个请求或每个 API worker 都重新创建持久化 Provider，相同宽表会被反复读取；如果直接增加多个独立进程，每个进程又会保留一份完整缓存，产生明显 I/O 和内存浪费。

项目需要区分“数据如何持久化”和“回测如何访问数据”。数据库可以提供查询能力，但不能自动消除回测过程中的查询、传输、反序列化和多进程副本。

## 选择

1. 继续使用 Parquet 作为市场数据的持久化、发布和恢复格式；物理文件按业务域组织为多字段宽表，具体布局由 ADR-017 定义。
2. 服务器启动时将选定发布版本一次性加载为只读 `MarketDataSnapshot`；正常回测不得访问 Parquet 或行情数据库。
3. 数值字段在内存中保存为共享日期轴、证券轴和按字段二维数组；分类字段使用整数编码和字典。
4. 生产使用 Linux，由父进程加载快照后 fork 固定回测进程池，通过 copy-on-write 共享物理内存页。
5. 基础数组不可修改；用户请求只创建自身计算中间结果，并受并发上限控制。
6. 数据更新采用新实例加载新快照、验证后切流、旧实例排空退出，不原地修改运行中的快照。
7. 数据库只在多服务器共享、实时写入、复杂在线查询或高频数据出现后增加；即使增加数据库，回测热路径仍使用内存快照。

## 备选方案

### 每个请求读取 Parquet

不采用。实现简单，但重复 I/O、解压和 DataFrame 构造会随着用户数增加。

### 每个 API worker 各自缓存

不采用为生产方案。它减少同一 worker 内的重复读取，但基础数据内存随 worker 数线性增长。

### 回测直接查询数据库

不采用为日频回测热路径。数据库增加服务部署、查询和数据传输成本，回测最终仍需将大块数据放入计算节点内存。

### 只保留内存、不保存 Parquet

不采用。服务重启、数据回滚、版本复现和离线重建都需要可靠持久化版本。

## 后果

### 正面

- 正常回测请求不再产生市场数据文件或数据库 I/O。
- 多个回测 worker 共享基础行情物理内存，避免每个 worker 一份完整副本。
- Parquet 继续提供简单、可移植、可校验和可回滚的冷数据版本。
- 运行中数据不可变，单次回测天然绑定一个一致快照。

### 负面与约束

- 生产部署需要 Linux 预加载/fork 启动器，普通多 Uvicorn worker 配置不能直接满足要求。
- 回测计算本身仍会产生中间数组，必须限制并发，不能只依赖基础快照共享。
- 滚动更新时可能短暂需要容纳新旧两份快照。
- 未来跨机器扩展时需要对象存储、共享数据服务或数据库，但这些不改变回测内存快照原则。
