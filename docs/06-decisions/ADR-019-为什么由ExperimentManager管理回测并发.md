# ADR-019：为什么由 ExperimentManager 管理回测并发

## 状态

已接受（2026-08-18）

## 问题

ResearchEngine 的 API 回测路由过去使用同步 `def`，因此回测执行隐式落入
FastAPI/Starlette 的通用线程池。旧版 `ExperimentManager` 只登记一次请求中的
`Experiment`，没有线程池、队列、任务状态、取消或并发上限，无法表达 ResearchEngine
的实际计算资源边界。

这会带来三个问题：

1. API 框架线程容量决定回测并发，ResearchEngine 无法按行情面板的内存开销限流；
2. 相同回测的并发请求只能依赖文件缓存锁，锁等待会占用 API 工作线程，超时后还可能重复计算；
3. 因子和策略回测没有统一的任务生命周期，无法返回 `run_id` 或查询排队状态。

## 决策

ResearchEngine 每个进程创建一个应用级 `ExperimentManager`，由它拥有并管理回测执行资源：

- 使用 Manager 自己的 `ThreadPoolExecutor`；
- 使用有界容量，默认最多同时执行 2 个回测、额外排队 8 个任务；
- 维护 `created → queued → running → succeeded/failed/cancelled` 状态；
- 以规范化任务键复用同键的进行中 Future；
- 队列满时返回 HTTP 429，而不是无限排队；
- FastAPI lifespan 只负责创建、启动和关闭 Manager，不负责执行回测线程；
- 因子、向量化策略和事件策略统一通过 Manager 提交；
- 进程内任务状态是临时运行状态，不作为跨实例可靠业务数据。

同步接口提交任务后等待 Future；异步接口返回 `run_id`，通过查询接口读取状态和结果。
任务真正执行仍由 Experiment/策略执行单元和 QuantCore 完成，Manager 不实现量化计算。

## 备选方案

### 方案 A：继续使用 FastAPI/AnyIO 通用线程池

实现简单，但并发上限由 Web 框架和部署参数间接决定，回测和普通同步接口共享资源，
无法做任务去重、队列拒绝和生命周期管理。因此不采用。

### 方案 B：每个请求创建一个 ExperimentManager

看似隔离，但每个 Manager 都会创建独立资源，无法限制进程级总并发，也不能跨请求复用
Future，继续存在重复计算和内存峰值问题。因此不采用。

### 方案 C：直接引入 Celery/Redis 等分布式任务系统

可以解决跨进程和重启恢复，但增加部署依赖、任务持久化和运维成本。当前 ResearchEngine
先解决单进程资源边界；未来多实例部署时，可将 Manager 的执行后端替换为外部队列，保持
提交、状态和结果接口不变。

### 方案 D：立即使用进程池执行所有用户代码

隔离能力更好，但进程启动和数据面板复制成本较高，现有 QuantCore 数据读取路径需要先做
基准测试。当前先保留执行后端抽象，线程池作为 MVP，用户代码生产部署仍需容器/子进程隔离。

## 后果

### 正面影响

- 回测并发有明确、可配置的上限；
- API 层不再决定回测计算线程；
- 同键并发请求只执行一次；
- 因子和策略任务可以统一查询、取消和观测；
- 后续切换进程池、远程 Worker 或 Redis 队列时，API 契约保持稳定。

### 负面影响

- 单进程重启会丢失运行中的 `run_id`；
- Uvicorn 多 worker 会创建多个独立 Manager，实际总并发等于 worker 数乘以每个 Manager 的并发；
- 线程无法安全强杀已经运行的用户 Python 代码；
- Manager 需要额外的状态、队列和并发测试。

## 实施边界

第一阶段采用单进程 Manager、线程池和本地缓存；同步 API 保持原响应契约，同时提供
`/api/experiments/*` 异步任务接口。多进程/多实例部署前，必须补充外部 RunStore、分布式
队列、分布式锁和结果存储，并将用户代码执行迁移到进程或容器隔离环境。
