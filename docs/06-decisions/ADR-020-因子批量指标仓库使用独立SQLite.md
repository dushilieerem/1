# ADR-020：因子批量指标仓库使用独立 SQLite

## 状态

已接受（2026-08-19）

## 问题

因子批处理需要跨日期保存批次状态、因子失败信息和少量标量指标。现有
`SQLiteStorage` 为单次实验快照存储，写入时会重建快照表，不具备历史批次、断点续跑或并发协调语义。

## 选择

新增 `Factor/database/factor_backtest.db` 作为独立指标仓库：

- 批次、因子运行、六行分组指标和 IC 汇总分别建表；
- SQLite WAL、busy timeout 和事务保证本地服务重启后可读；
- 批处理协调器是唯一写入者，Worker 只返回内存标量；
- `MarketData/current` 作为 MVP 数据源，不记录数据指纹；
- HTTP 只读查询，任务由 CLI 或外部调度器触发。

## 备选方案

### 复用现有 `SQLiteStorage`

会覆盖单次快照、无法自然表达多日历史，也会把曲线存储职责与批次仓库混在一起，因此不采用。

### PostgreSQL/ClickHouse

更适合多实例和大规模明细，但当前只需单机内网标量仓库，新增部署和运维成本过高；暂不采用。

### Celery/Redis

可提供跨进程任务持久化，但 MVP 先依托 `ExperimentManager` 和任务计划，避免引入新的运行时依赖。

## 后果

正面：实现小、部署简单、历史查询清晰、与单次实验存储解耦。负面：SQLite 受单写者和单机限制，
且没有数据版本指纹，若当前数据被替换，历史结果不能自动解释为同一数据版本。

## 升级条件

满足任一条件时评估 PostgreSQL/ClickHouse：多实例同时写入、批次/指标规模导致 SQLite 写入成为瓶颈、
需要每日 IC 明细或净值曲线查询、或需要权限/多租户和分布式任务恢复。迁移时保留批次键和指标版本，
先做双写/校验，再切换只读查询。
