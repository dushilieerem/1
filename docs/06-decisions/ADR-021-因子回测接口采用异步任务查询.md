## ADR-021: 因子回测接口采用异步任务查询

### 问题

因子回测会执行用户 Python 代码、读取较大的行情面板并扫描缓存数据指纹。同步
`POST /api/backtest/factor` 会长时间占用 WebApp 到 ResearchEngine 的 HTTP 连接，
上游代理超时后可能返回 HTTP 502；同时，提交请求本身无法表达排队、运行中和取消状态。

### 选择

将单因子和批量因子回测的提交接口统一为异步任务提交接口：

- `POST /api/backtest/factor` 提交成功立即返回 `202`、`run_id`、相对 `poll_url`、
  `Location` 和 `Retry-After`。
- 新增 `GET /api/backtest/factor/{run_id}` 查询任务生命周期；成功时在 `result` 中返回
  原有完整 `FactorBacktestResponse`。
- 新增 `DELETE /api/backtest/factor/{run_id}`。排队任务实际取消并释放队列容量；运行中
  任务只记录 `cancel_requested`，不强制终止用户 Python 线程。
- 因子代码、数据和执行异常统一为 `status=failed` 与顶层 `error`。
- 任务状态暂存于单个 ResearchEngine 进程内存，终态保留 60 秒后清理并释放完整结果。
- 因子提交使用请求哈希进行进程内同请求去重；真实文件缓存键继续包含缓存版本、请求
  参数和行情数据指纹，且指纹与缓存扫描放在工作线程中。
- `POST /api/internal/factor-backtest-batches` 立即返回 `202`、`task_id`、相对
  `poll_url` 和 `created_at`；`GET /api/factor-backtest-batch-tasks/{task_id}` 返回
  `queued/running/succeeded/failed` 状态以及完成后的 `batch_id`、`batch_url` 和结果。
- 批量任务使用独立的单线程协调执行器；协调器不提交到 `ExperimentManager`，单因子实验
  仍使用共享 Manager 的两个 worker。批次进度和结果由 SQLite 长期保存，任务快照只保留
  60 秒；相同非 `force_retry` 请求在进程内去重，`force_retry` 创建新任务。

### 备选方案

1. **继续同步等待**：实现简单，但无法消除代理超时和长连接占用，也无法提供可靠的排队与取消状态。
2. **兼容旧 POST 与新增异步 POST**：可以渐进迁移，但同一路径需要同时维护两种响应契约，
   容易让调用方误解析 `202`；本次直接替换契约，不保留旧批量路径兼容层。
3. **Redis/数据库任务队列**：可以支持多实例和服务重启恢复，但当前 ResearchEngine 尚处于
   单进程部署阶段，会引入额外基础设施、任务序列化和结果存储成本；后续跨进程需求出现时再演进。
4. **强制杀死运行中线程**：Python 线程无法安全地终止任意用户代码，强杀会破坏进程状态；
   如需硬超时，应改用受限子进程或容器执行器。

### 后果

正面影响：提交请求快速结束，WebApp 可以展示排队/运行状态；代理 502 风险降低；队列满、
失败和取消都有明确的机器可读语义；缓存和数据指纹不再阻塞 POST。

负面影响：ResearchEngine 与 WebApp 必须协调发布，旧版 WebApp 不能继续把 POST 响应当作
完整回测结果；单进程内存任务表要求只使用一个 Uvicorn worker/实例；任务状态必须在 60 秒内取走
并持久化，服务重启或进程故障不会恢复内存中的任务。
