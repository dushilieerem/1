# SVQuant 部署文档

## 1. 部署边界

本仓库提供 SVQuant 产品前后端的本地开发启动方式。PostgreSQL 和 ResearchEngine（RE）是独立依赖，需先由各自环境部署并可访问。本仓库目前没有定义生产环境的反向代理、进程守护、容器编排、高可用或自动回滚方案；生产部署按实际运维方案执行，不应将本地启动脚本视为生产部署器。

## 2. 环境准备

- Linux Bash 环境，具备 `setsid`、`curl` 和可用的 `conda`。
- 项目 Conda 环境 `svquant` 已安装后端依赖。
- `frontend/node_modules/` 已安装 Vite 依赖。
- PostgreSQL 可访问；RE 已独立启动并可从 SVQuant 后端访问。
- `backend/.env` 已从 `backend/.env.example` 创建并配置。

首次准备环境时，在仓库根目录执行：

```bash
cp backend/.env.example backend/.env
conda activate svquant
pip install -r backend/requirements.txt
npm --prefix frontend install
```

然后按部署环境编辑 `backend/.env`。如果 Conda 环境尚未创建，应按团队 Python 环境规范先准备环境；本项目不在启动脚本中自动安装依赖。

至少确认以下配置存在且值正确：

| 配置 | 用途 |
|---|---|
| `DATABASE_URL` | SVQuant PostgreSQL 连接 |
| `JWT_SECRET_KEY` | SVQuant 登录令牌签名密钥，部署时必须设置为随机密钥；缺失或弱值会导致后端启动失败 |
| `YG_RE_BASE` | ResearchEngine 服务地址 |

`.env.example` 中的地址、默认管理员信息和密钥仅供本地示例使用；首次部署前必须检查并替换不安全的默认值。`.env`、密码、Token 和密钥不得提交到 Git 或复制到文档中。

## 3. 一键启动

### 社区帖子AI摘要

社区摘要优先使用SVQuant明确配置的`LLM_*`；未配置时，自动通过已有`YG_RE_BASE`
调用ResearchEngine的`POST /api/ai/post-summaries`，复用AI因子生成使用的模型地址、模型名和密钥。
密钥继续只放在ResearchEngine端，不需要复制到SVQuant，也不需要安装本地模型。

发布顺序：先部署包含摘要接口的ResearchEngine，再部署本次SVQuant后端修改。
ResearchEngine已能生成AI因子时，无须新增模型配置。不要将因子生成接口当作摘要接口调用。

验收时在帖子中点击“生成摘要”重新生成，不使用旧的浏览器摘要缓存。
接口返回`board.artifacts.summary_source=llm`，页面应显示“AI摘要”。模型超时、无效结果或
摘要接口尚未部署时明确报错；不会把原文节选冒充AI摘要。
没有独立LLM且没有RE的纯本地环境，仍保留明确标注的“原文节选（非AI）”。

在仓库根目录运行：

```bash
./scripts/svquant.sh
```

脚本启动后端 `8766` 端口和前端 `9530` 端口，最多等待 60 秒进行健康检查。前端默认访问地址为 <http://127.0.0.1:9530>，后端 API 文档为 <http://127.0.0.1:8766/docs>。脚本将进程置于独立后台会话；关闭启动终端不会向服务发送中断信号。

```bash
./scripts/svquant.sh status    # 查看服务状态
./scripts/svquant.sh logs      # 跟踪日志；Ctrl+C 只退出日志查看
./scripts/svquant.sh restart   # 重启
./scripts/svquant.sh stop      # 停止脚本启动的服务
```

可通过 `SVQUANT_CONDA_ENV` 指定 Conda 环境名（默认 `svquant`）；找不到 Conda hook 时可设置 `SVQUANT_CONDA_HOOK`。运行日志和 PID 文件写入被 Git 忽略的 `backend/output/dev-services/`。

## 4. 手动启动

```bash
conda activate svquant
cd backend
python -u api_server.py
```

另开终端启动前端：

```bash
cd frontend
npm run dev
```

启动顺序为：PostgreSQL 与 RE → SVQuant 后端 → 前端。SVQuant 不启动或管理 RE。

## 5. 健康检查与故障定位

```bash
curl http://127.0.0.1:8766/api/health
./scripts/svquant.sh status
./scripts/svquant.sh logs
```

若服务无法就绪，先检查 `backend/output/dev-services/` 中的日志，再确认 PostgreSQL、`backend/.env`、Conda 环境、前端依赖和 RE 地址。浏览器不能直接访问 RE；RE 连接问题应从 SVQuant 后端日志和 RE 服务状态两侧排查。

## 6. 定时任务：因子面板日更

因子面板的指标缓存（PostgreSQL `factor_dashboard_metrics`）由 `backend/scripts/daily_dashboard_refresh.py` 批量调 RE 回测填充。默认跑**面板全量组合**：沪深300 / 中证500 × 近3月/1年/3年 × 过滤涨停开/关 = **12 组**，单因子约 6–10 秒、331 个因子单组约 0.5–1 小时，**全量约 10–12 小时**，必须后台或定时执行。

只跑 RE 实际支持的股票池：RE 对其余池直接 422（`不支持的股票池 'CSI1000'，可用: ['ALL_A','A_SHARE','CSI300','CSI500','CSI_ALL']`），因此股票池收敛为 CSI300 / CSI500，前端面板也只展示这两个。

### 进程内定时器（默认开启，无需 cron / systemd / 计划任务）

调度做在 SVQuant 后端进程内部（`services/factor/dashboard_scheduler.py`）：进程启动即起一个
daemon 线程，到点跑一遍全量组合。**不需要 root、cron、systemd 或 Windows 计划任务**，
只要后端进程在跑（`./scripts/svquant.sh` 以独立会话启动，关闭终端不会中断）。

`.env` 配置（均可省略）：

| 配置 | 默认 | 说明 |
|---|---|---|
| `SVQUANT_PANEL_DAILY_ENABLED` | `1` | 置 `0` 关闭进程内日更 |
| `SVQUANT_PANEL_DAILY_AT` | `00:00` | 每天触发时刻（本机时区，HH:MM） |
| `SVQUANT_PANEL_DAILY_GRACE_MIN` | `120` | 触发时刻进程不在线时，多久内启动仍补跑一轮 |

启动日志会打印一行确认，例如：

```
  panel daily scheduler: 每天 00:00 · 12 组 · 补跑窗口 120min
```

运行状态落在 `backend/output/factor_dashboard/panel_daily_state.json`（`last_run_date`、
上轮 ok/failed、耗时），进度仍在 `job.json`，日志在后端进程输出里（`[panel] ...` 前缀）。

局限（选这条路的代价）：

- **进程不在线就错过**。后端进程停着的时候不会跑；重新启动时只在 grace 窗口内补跑。
  真要"机器重启也必跑"，仍需外部调度（systemd timer / cron / 计划任务）。
- 全量约 10–12 小时跑在 API 进程的一个线程里，期间不要重启后端（重启会中断该轮）。

手工触发（不影响定时器，二者靠 flock 互斥）：

```bash
backend/scripts/run_daily_dashboard.sh                   # 全量 12 组
backend/scripts/run_daily_dashboard.sh --combo CSI300:3y # 单个组合
```

### 并发与重叠保护

面板整批回测持有**跨进程 `flock`**（`backend/output/factor_dashboard/panel_refresh.lock`），API 的
「刷新指标」按钮、进程内定时器与命令行日更三者互斥：上一轮未结束时，本轮不再并发执行，
而是写 `job.json` 的 `status=failed` 并在日志里告警后中止，避免两批并发压 RE、交叉写同一张表。

RE 侧回测线程池约 40 且与试算/回测共享：全量日更会长时间占满该池，影响他人交互式因子检测，排期时需知悉。
