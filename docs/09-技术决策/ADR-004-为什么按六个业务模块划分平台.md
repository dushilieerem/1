# ADR-004：为什么按六个业务模块划分平台

> **决策记录**：Architecture Decision Record  
> **日期**：2026-07-20  
> **状态**：已接受  
> **关联**：`../01-需求文档/产品能力地图.md`、`../02-架构文档/system_architecture.md`

## 问题

现有架构主要以 `QuantCore`、`ResearchEngine`、`TradingEngine` 三个技术组件描述，能够说明量化计算链路，但无法清晰定义面向 SaaS 产品的用户、行情数据、新闻、社区、研究和交易职责。若继续将这些能力混在“ResearchEngine”或笼统的“SaaS 应用层”中，后续会出现资产归属、权限、数据所有权和服务依赖不清的问题。

## 选择

平台按以下六个业务模块定义边界：

1. 用户模块：账号、组织、权限、计费、额度和资产归属。
2. 数据模块：行情、基本面、指数、行业分类和数据质量。
3. 新闻模块：新闻、公告、研报、政策事件及关联、检索和语义分析。
4. 社区模块：内容、互动、协作、研究资产分享和审核。
5. 研究模块：因子研究、策略研究、回测、指标、归因、报告和 AI 研究辅助。
6. 实盘/模拟盘模块：策略部署、账户、模拟撮合、风控、订单与执行。

`QuantCore` 保持为数据、研究和交易可复用的量化计算内核；`ResearchEngine` 保持为研究模块的无状态回测计算服务；`TradingEngine` 承载实盘/模拟盘模块。该决策定义业务与接口边界，**不要求现阶段立即拆成六个独立进程、仓库或数据库**。

## 备选方案

### 继续沿用三技术组件作为产品模块

不采用。它不能表达用户、新闻和社区的独立业务职责，且容易误把因子资产管理、社区内容或用户权限塞入回测服务。

### 立即建设微服务与独立数据库

不采用。当前处于 0-1 阶段，过早分布式拆分会引入部署、调用、鉴权和运维成本。先稳定接口、数据所有权和领域模型，待并发、团队边界或独立扩展需求明确后再拆分部署。

## 后果

### 正面后果

- 产品路线、Initiative 和 Feature 可以按用户价值和业务责任拆分。
- ResearchEngine 的边界明确：只执行研究计算，不管理因子库、用户或社区。
- 数据和新闻成为共享能力，避免研究和交易各自维护不一致的数据口径。
- 实盘/模拟盘能够在策略发布、权限、审计与风控边界内逐步建设。

### 负面后果与约束

- 新 Feature 必须标明所属业务模块、输入数据所有者和依赖模块。
- 跨模块调用必须经由契约接口，不能直接读写对方的内部存储。
- 用户、社区和新闻模块尚未实现，当前仅完成产品与架构边界定义。
