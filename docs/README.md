## 推荐阅读顺序

1. 从[产品需求文档](01-需求文档/产品需求文档.md)和[产品能力地图](01-需求文档/产品能力地图.md)理解目标与边界。
2. 阅读[系统架构](02-架构文档/system_architecture.md)和[回测集成设计](02-架构文档/engine-design.md)，了解 SVQuant 与 ResearchEngine 的职责划分。
3. 按具体工作进入对应 [FEAT 功能包](03-模块详细设计/README.md)，查看范围、设计和验收记录。
4. 涉及持久化、接口、验证或启动时，分别查阅数据库、API、测试和部署目录。
5. 需要了解决策理由或当前交付状态时，再查看 ADR 和项目管理目录。

## FEAT 功能包约定

`03-模块详细设计/FEAT-*` 是功能的交付单元。已有功能包可能包含产品需求、技术设计、字段字典或验证记录；这些资料继续放在同一功能包内，避免拆散上下文。只有存在实际设计对象时才增加类设计、流程图或专项文件，不要求每个模块机械地具备所有模板章节。

## 系统边界

- SVQuant 负责产品页面、用户与权限、产品数据、BFF、展示缓存和用户操作。
- ResearchEngine（RE）负责研究计算、因子/策略执行、行情访问及研究任务结果；SVQuant 通过 HTTP API 集成，不导入 RE 的 Python 包。
- RE 内部实现和权威 API 契约由 [ResearchEngine 独立仓库](https://gitee.com/yanggu-yuanqi-intelligence/research-engine)维护；本仓库只记录产品级需求、跨仓库接口和 SVQuant 侧适配。
- 涉及 PostgreSQL 的表清单可由 `backend/scripts/refresh_database_docs.py` 从已配置的数据库生成；生成结果可能包含经过脱敏的样例数据，不应手工填入密钥或用户敏感信息。

## 文档维护原则

- 一个结论只有一个权威位置；其他文档通过链接引用，避免复制形成不一致。
- 接口以运行中的 OpenAPI 和服务所有者维护的契约为准；提案文档会明确标注尚未实现的内容。
- 需求、架构和验收结论应与当前代码及部署边界一致；旧决策保留在 ADR 或历史归档，不冒充当前状态。
- 文档深度跟随决策复杂度。没有实际类关系、额外流程或测试目标时，不创建空壳文档。
