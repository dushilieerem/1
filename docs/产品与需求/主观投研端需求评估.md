# 主观投研端需求评估

> 命名约定：本轮产品称「主观投研端」；原 `量化机构端PRD.md` 描述的是「量化机构端」，两者业务模型不兼容。

| 项 | 内容 |
| --- | --- |
| 评估对象 | 《旸谷资本 AI 主观价值投资平台 · 需求文档 v1.1》（2026-10-30）及其依据的 V0.6 原型、《AI 角色与能力清单》 |
| 评估日期 | 2026-10-30 |
| 评估结论 | **可立项，但不能按 112 条 FR 全量开工；需要先定为独立产品线，按三期收敛** |
| 估算口径 | 初步估算（±40%），不含数据采购、法务合规与客户验收等待时间 |

---

## 1. 一句话结论

这不是"给 SVQuant 加一个端"，而是在现有量化投研产品之外**新增第二条产品线**：业务对象从"因子/策略/回测结果"变成"公司/证据/议案/授权"，核心能力从"算得快"变成"流程可审计、权限可证明、结论可追溯"。

工程基建（账号、审计、AI 路由、知识库、行情网关、前端框架、测试）约 20–25% 可复用；**业务域 0% 可复用**。真正的瓶颈不在前端，而在三件事：证据数据的供给、审批/授权版本模型、合规责任边界。

## 2. 需求体量与性质

### 2.1 量化画像

| 维度 | 数量 | 说明 |
| --- | --- | --- |
| 工作区 | 9 个 | 驾驶舱、机会发现、公司研究、辩论室、组合、投委会与审批、执行、投后退出、关于我们 |
| 角色 | 6 个 | 投资经理、合伙人、Chairman、独立风控、交易执行、组合监控（另有"人类责任岗位"） |
| 功能需求 | 112 条 FR | 覆盖 9 个工作区与全局框架，P0 要求"自动化测试或人工审计证据" |
| 业务规则 | 12 条 BR | 仓位/现金上限、职责分离、版本绑定、硬阻断、AI 边界 |
| 原型自诊断缺口 | 12 条 GAP | 需求方自己已列出：单一 Proposal 模型、执行由授权驱动、数据深度、AI 真实性、SSO/RBAC、持久化、双语残留、发行人聚合、交易规则、观察池、导出 |
| AI 岗位 | 25 个（AI-01…AI-25）+ 11 项通用能力 | 覆盖七个业务阶段 |
| 演示对象 | 24 家公司 | A 股/美股/港股各 8 家；仅贵州茅台有完整六维数据（GAP-03） |

### 2.2 性质判断

- **它是一套"带 AI 的受控决策流程系统"**，不是分析工具。价值在流程与取证，不在图表。
- **关键实体是版本化的**：研究版本、议案版本、配置版本、批准版本、授权快照、政策版本。任一实质变更必须使旧批准/授权失效（BR-04、FR-APR-10/12、FR-RES-15）。这是全系统最难、也最不能做错的部分。
- **职责分离是硬规则**：提案人不得自批、审批人不得下单、风控不得改研究、监控不得审批（§2.3）。这类规则必须在服务端强制执行，前端隐藏菜单不算安全边界。
- **原型只是交互样机**：V0.6 是单文件 708KB / 4,734 行、状态存 sessionStorage、Agent 用定时器与写死文案模拟、含多层覆盖式补丁（同一页面被重复定义多次）。它可以当"需求说明书 + 视觉参考"，**不能当技术设计**。

## 3. 与 SVQuant 现状的差距

### 3.1 能力对照

| 能力 | SVQuant 现状 | 结论 |
| --- | --- | --- |

| 组合风控规则 | 无；RE 回测侧有市场规则，但不是组合风控 | 新建规则引擎 |
| 交易执行 | 无券商适配；模拟盘是"策略日终结算"，不是人工授权订单流 | 新建 SimBroker + 订单/成交/对账 |
| 投后监控与退出 | 无 | 新建 |
| AI 路由 / 额度 / 护栏 | `ai/router` TaskSpec（ADR-037）、`ai_usage` 配额、`metrics_trust` 护栏 | 复用并扩展 |
| 多 Agent 长任务 | 无任务队列；以同步调用为主 | 新建（defer + 任务状态机） |

| 双语 | 无 i18n 基础设施，全中文硬编码 | 新建（约 4 万字文案 + 数字/币种/实体一致性） |
| 测试 | 前端 node:test + Testing Library，后端 pytest，根目录 Playwright | 复用，需建 FR → 测试追踪矩阵 |

### 3.2 已有的两份"机构端"会撞车

`docs/产品与需求/量化机构端PRD.md`（v0.2，2026-10-28）描述的是**量化机构端**：因子 → 策略 → 研究审批 → 风控复核 → 基金决策 → 托管 → 产品。本次需求是**主观价值机构端**：公司研究 → 辩论 → 议案 → 两级审批 → 执行 → 投后。

两者复用不了业务模型，却共用"机构端"这个名字。若不先定名与定位，后续路线图、菜单、PRD、销售口径会持续冲突。

**建议**：现有文档改称"量化机构端"，新增的称"主观投研端 / 价值投资端"；或明确前者为"研究型机构版"、后者为"资管决策版"。

## 4. 技术方案初判

### 4.1 边界与形态

- **新的限界上下文**：`institution`（或 `discretionary`）域，独立 `services/` 包 + 独立路由前缀 `/api/inst/*`；**不塞进** `factor` / `strategy` / `paper` 任何现有模块。
- **前端形态**：同一 SPA、独立 Layout 与路由树（`/inst/*`），不复用消费级 Navbar。独立 Vite 应用也能做，但会多一套部署与登录态同步，首版不建议。
- **数据隔离**：机构数据按 `org_id` 隔离；演示环境与试点环境用不同 schema/库，禁止演示数据进入真实审批（BR-11）。

### 4.2 必须新建的核心模型

```text
org / membership / role_assignment
company / security_master
research_case → research_version → research_package → evidence(来源/时间/版本/授权范围)
debate_session → round → argument(绑定 evidence_id) → dissent
proposal → proposal_version → partner_config → risk_check → approval
authorization(不可变快照) → order → fill → reconciliation
position_snapshot / exposure / monitoring_event / exit_case
audit_event(领域级，含版本与政策)
```

关键设计约束：

1. **版本失效用事件表达**，不要用 `UPDATE stage`。原型 GAP-01 正是"多套状态并存"导致的授权链断裂。
2. **授权是不可变快照**，只增不改；撤销写新记录（FR-APR-31/33）。
3. **硬阻断在服务端**：单股 >15%、交易后现金 <10%、版本不一致、无有效批准 → 直接拒绝，任何角色（含 Chairman、AI）不能绕过（FR-APR-14/20、BR-07）。
4. **AI 产物落库必须带**：模型/政策版本、证据 ID、时间、真人确认状态（FR-APR-29）；无证据 ID 的重大结论不得进入审批包（BR-08）。

### 4.3 AI 侧

现有 `ai/router` 适合"单次任务"，不够支撑 25 个岗位。建议：

- 每个 AI 岗位注册 TaskSpec（可审计、可换模型、可计费），但**确定性逻辑（阈值、有效期、版本校验、状态流转）一律用代码，不用模型**——这与《能力清单》结尾的提醒一致。
- 正/反方使用**隔离上下文**（不同检索集、不同任务、先独立成稿再交换），否则"辩论"退化为同一模型自说自话。
- 增加引用校验器：论点必须绑定存在的 `evidence_id`，引用不存在的证据直接拦截（原型研讨厅已有此规则，应继承）。
- AI Chairman 的"自动批准"只允许在演示政策内、且有金额/仓位/账户硬上限；生产环境必须默认关闭。

### 4.4 执行侧

首版只做 SimBroker（纸面撮合 + 幂等 + 对账 + 人工处置），不做真实券商。需求 §1.2 明确"本期不包含真实资金交易、券商正式下单"，但 FR-EXE-08/09 又要求真实券商适配与 QMT——**这两处自相矛盾，需要需求方确认以哪条为准**。

## 5. 工作量与周期（初步估算）

| 工作流 | 人周 | 说明 |
| --- | --- | --- |
| 组织 / 角色 / 权限 / SoD | 2–3 | 服务端 RBAC、6 角色、菜单与按钮门禁 |
| 前端 9 工作区 | 12–16 | 机构壳、研究页、辩论页、审批台、执行页、投后台 |
| 研究域（六维、资料包、版本、估值） | 6–8 | 含 DCF 参数化与敏感性表 |
| 议案 / 审批 / 授权状态机 | 8–12 | 最难；版本绑定、失效、快照、门禁 |
| 风控规则与执行前复核 | 4–6 | 阈值引擎 + 组合/发行人聚合 |
| 执行与对账（SimBroker） | 4–6 | 幂等、部分成交、异常处置 |
| 投后监控与退出 | 4–6 | 论点台账、预警、退出议案 |
| AI 编排与岗位接入 | 8–12 | 25 岗位分批；引用校验、隔离上下文 |
| 证据数据接入 | 8–14 | 不含采购/授权谈判等待 |
| 设计（视觉/交互/无障碍） | 5–8 | 原型可参考，不能直接搬 |
| 双语 + 导出 + 审计留痕 | 4–6 | 4 万字文案、JSON 导出、领域审计 |
| 测试与验收证据 | 6–8 | 112 条 FR 的追踪矩阵 |
| **合计** | **约 70–95 人周** | 4–5 人团队约 4–5 个月到"可试点"，6 个月+ 到全量验收 |

对照：一个"演示级可跑通"的版本约 22–28 人周（3 人约 8–10 周），前提是**用演示数据、单市场、3–5 家公司、中文单语、SimBroker**。

## 6. 风险清单

| # | 风险 | 等级 | 影响 | 缓解 |
| --- | --- | --- | --- | --- |
| R1 | 证据数据供给不足（仅 1/24 公司数据完整；无美股/港股基本面与公告） | 极高 | 六维研究与估值变成"编数据"，直接违背 BR-08 与 GAP-03 | 首版只承诺 1 个市场 + 3–5 家精修；数据源与授权先行立项 |
| R2 | 合规与责任边界（AI Chairman、AI 自动批准、投资建议定性、审计留存） | 极高 | 产品可能被认定为无资质投顾或误导性演示 | 全程"模拟环境"标识；AI 仅建议；自动批准默认关闭；法务前置评审 |
| R3 | 审批/授权版本模型做错 | 高 | 出现"有批准无授权仍可执行"（GAP-02）、旧状态串用（GAP-01） | 事件化 + 不可变快照 + 状态机测试；先写 ADR 再写代码 |
| R4 | 与既有量化机构端定位冲突 | 高 | 文档、路线图、销售口径互相打架 | 先定名与产品组合，再开需求评审 |
| R5 | AI 可信度（幻觉、伪独立辩论、伪造证据） | 高 | 研究结论不可用，合规风险 | 证据 ID 强校验、正反隔离、输出标注模型/政策版本、人工确认门槛 |
| R6 | 范围蔓延（112 条 FR 一次交付） | 高 | 周期失控、质量下降 | 按工作区分期，P0 再切"最小闭环" |
| R7 | 双语与无障碍（4 万字、无 i18n 基建） | 中 | 英文版不可用，验收不通过（FR-GLB-02/07） | 文案资源化 + 自动扫描；首版可只交付中文并保留 i18n 结构 |
| R8 | 执行适配（QMT 仅 Windows、市场规则、幂等） | 中 | 执行页失真或事故 | 首版 SimBroker；真实适配单独立项 |
| R9 | 组织/SSO 缺失 | 中 | 无法多人协作与真实分权（GAP-06） | 阶段 2 接 SSO；演示期用切换身份并明确标注 |
| R10 | 需求内部矛盾（真实交易 vs 本期不做；净值核算 vs 参考净值） | 中 | 验收口径不一致 | 需求评审逐条澄清，形成基线 v1.2 |

## 7. 建议的分期

### 阶段 0：可研与定稿（2 周，1 产品 + 1 架构 + 1 设计）

- 定名与产品组合：与量化机构端的关系、目标客户（旸谷定制 / 通用产品）、交付形态（子路由 / 独立应用 / 私有化）。
- 数据可行性：A 股财报/公告/一致预期的来源与授权；美股/港股是否首版。
- 合规前置：AI 边界、演示标识、审计留存、责任岗位。
- 产出：需求基线 v1.2（消除 §4.4 类矛盾）、领域模型与 ADR、范围裁剪表、验收矩阵。

### 阶段 1：演示闭环（8–10 周，3–4 人）

单市场 + 3–5 家精修公司 + 演示数据；6 角色演示身份；9 工作区骨架；研究 → 辩论 → 议案 → 两级审批 → 执行前复核 → SimBroker → 投后，全链路可点通；领域审计；中文。

**验收**：一条议案从立案到模拟成交全程可追溯；任一实质变更使旧批准失效；硬阻断不可绕过。

### 阶段 2：受控试点（+8–10 周）

真实 A 股数据源接入；组织与角色落库；风控规则引擎；导出与报告；双语；自动化测试覆盖 P0；性能与并发。

### 阶段 3：生产合规（+8–12 周）

SSO/多机构；美股/港股数据；真实券商适配（若确认要做）；审计 WORM 与留存；私有化部署；渗透与压测。

## 8. 需要先确认的决策点

1. **目标客户与形态**：旸谷资本单租户私有化，还是 SVQuant 通用产品的一个版本？
2. **与现有量化机构端的关系**：替换、并存，还是改名区分？
3. **首版市场与标的**：三市场 24 家（照需求文档），还是单市场 3–5 家（可验证）？
4. **数据来源**：自采、采购，还是客户提供？谁承担授权与合规责任？
5. **AI 边界**：AI Chairman 与"AI 自动批准"是否进首版？生产是否默认关闭？
6. **执行**：只做 SimBroker，还是首版就要 QMT/真实券商（与 §1.2 冲突）？
7. **责任主体**：资金授权、模型治理、风险政策、异常处置的真人岗位由谁担任？
8. **资源**：与量化主线（因子/策略/回测）争抢同一批人时，优先级如何排？

## 9. 结论

**值得做，但要按"新产品线"立项，不能按"加一个端"排期。**

- 需求文档质量高于一般原型：角色边界、职责分离、版本失效、负面规则、审计要求都写清楚了，且自己列出了 12 条缺口——这降低了产品风险。
- 真正的风险集中在数据、合规、审批模型三处，而不是页面数量。先把这三件事定下来，再谈 112 条 FR。
- 建议下一步：用 2 周做阶段 0，产出需求基线 v1.2 + 领域模型 ADR + 数据可行性结论 + 分期范围；拿到"数据可供给、合规可接受、范围可裁剪"三个确认后再进入开发。

**Go / No-Go 判据**：数据授权可落地、合规责任主体明确、客户接受"先演示后试点"、与量化主线资源不冲突。四项任一不成立，先不要开工。
