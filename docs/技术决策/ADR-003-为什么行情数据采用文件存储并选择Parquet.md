# ADR-003: 为什么行情数据采用文件存储，并选择 Parquet

> **决策记录**：Architecture Decision Record
> **日期**：2026-07-17
> **状态**：已实施

## 背景

SVQuant 当前以本地 CLI/SDK 形态服务量化研究。A 股历史行情、基本面等原始数据由用户自行准备，主要特点是：批量导入、读多写少、按字段读取，并在因子计算与回测时加载为“日期 × 标的”的面板数据。

本决策回答两个问题：

1. 行情原始数据为什么优先存为本地文件，而不是要求部署数据库？
2. 在 CSV、Pickle 与 Parquet 中，为什么选择 Parquet 作为标准落盘格式？

本决策仅适用于**历史行情和基本面原始数据**。回测结果、用户配置及未来 SaaS 的共享数据可根据场景使用 CSV、SQLite、ClickHouse 或其他服务端存储。

## 决策

1. 当前阶段的历史行情与基本面数据采用**本地文件存储**；数据目录由用户提供，不随代码仓库分发。
2. 标准格式采用 **Parquet**；股票日频数据的物理文件按业务域组织为多字段宽表，具体 schema 和读取适配由 ADR-017 定义。
3. `IDataProvider` 保留 CSV、Parquet、ClickHouse、AkShare、Wind 等实现，作为导入、兼容或特定部署场景的适配方式；它们不改变 Parquet 作为默认原始数据格式的选择。
4. 当出现实时写入、多用户共享、服务端低延迟查询或复杂关联查询的明确需求时，重新评估并可引入 ClickHouse 或其他数据库。

## 为什么选择文件而不是数据库

| 维度 | 本地文件（当前选择） | 数据库（当前不作为默认） |
|------|----------------------|--------------------------|
| 研究工作负载 | 批量读取后进入 Pandas/NumPy 做向量化计算，匹配主要链路 | 数据库查询后仍需将大块数据传入内存，未减少核心计算量 |
| 部署与成本 | 用户准备目录即可运行，无服务、账号、网络或运维负担 | 需要部署、备份、监控、权限、迁移与连接管理 |
| 数据更新方式 | 行情通常按日或按批次更新，生成新文件即可 | 事务与持续写入能力在当前场景中利用率低 |
| 离线可复现 | 同一份数据目录可随研究环境复制、校验和归档 | 依赖数据库实例的状态、版本和连接配置 |
| 并发与实时能力 | 不适合频繁并发写入 | 适合多用户共享、实时摄入和在线查询 |

**结论**：在 0-1 阶段，文件存储以更低的交付与使用成本满足“历史数据批量分析”的主场景。数据库不是被否定，而是留给其优势真正重要的阶段和场景。

### 何时升级为数据库

满足任一条件时，应新建 Feature 并重新评估本决策：

- 多个用户或服务实例需要共享同一份数据并进行权限隔离；
- 行情需要持续、实时地写入并被在线查询；
- 需要大量跨数据集的 SQL 聚合、筛选或审计；
- 本地文件无法满足数据量、并发或远程访问的性能目标。

## 为什么在 CSV、Pickle 和 Parquet 中选择 Parquet

| 格式 | 优点 | 不作为标准行情格式的原因 |
|------|------|--------------------------|
| CSV | 通用、可直接查看，适合小型导入导出文件 | 文本解析开销大、文件通常更大、类型与 schema 约束弱；读取大面板时效率和存储成本不理想 |
| Pickle | Python/Pandas 对象序列化方便，适合短期本地缓存 | Python 专用、跨版本与跨语言兼容性弱；不能加载不可信文件，且缺少适合数据分析交换的稳定 schema |
| **Parquet（选择）** | 列式、带类型 schema、压缩好；与 PyArrow/Pandas 兼容；可按列读取 | 不擅长随机更新，因此采用批量生成新文件的更新方式，而非逐行写入 |

Parquet 与当前面板计算方式直接匹配：

- 相关字段按业务域集中，Provider 仍可通过列投影向上层提供 `close`、`volume` 等单字段面板；
- schema 保留字段类型，减少 CSV 文本解析与类型推断；
- 文件具有可移植性，可在 Python 以外的分析工具中读取，不把数据资产锁定在 Python 对象序列化格式中；
- 压缩后的列式文件更适合长期保存较大规模的历史面板。

## 数据组织方式

```text
ResearchEngine/marketdata/<release>/
├── panels/
│   ├── market_data.parquet
│   ├── daily_basic.parquet
│   └── security_status.parquet
├── display/
│   └── unadjusted_price.parquet
└── data_manifest.yaml
```

股票日频宽表以日期为行，使用 `(symbol, field)` 两级列。读取器建立 `field → 业务域文件及物理列` 映射，`DataEngine` 对上层屏蔽具体存储格式。完整目录与字段契约见 FEAT-024。

## 后果

### 正面后果

- 新用户无需部署数据库即可开始研究，符合 CLI/SDK 阶段的低门槛目标。
- 原始数据读取与向量化因子、回测计算的内存模型一致。
- 数据格式有稳定 schema，便于批量处理、迁移和长期归档。
- 通过 `IDataProvider` 保持后续迁移到数据库或接入其他数据源的能力。

### 负面后果与约束

- 文件不提供事务、行级并发写入、统一权限管理和服务端查询能力。
- 数据更新必须采用批处理并生成新 release，禁止多个进程覆盖活动版本文件。
- Parquet 不适合作为人工直接编辑的格式；数据修订应通过导入/转换任务生成新文件，而不是手工修改。
- CSV 仍可用于样例、小型导入导出和人类可读的回测产物；Pickle 仅可用于受信任环境下的临时缓存，不作为原始行情交换或归档格式。
