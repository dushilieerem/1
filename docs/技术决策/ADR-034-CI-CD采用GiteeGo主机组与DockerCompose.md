# ADR-034: CI/CD 采用 Gitee Go 自建主机组 + Docker Compose

- 日期：2026-10-30
- 状态：已接受
- 关联：`../部署与运维/CI-CD.md`、`ADR-006`、`../../deploy/compose.yml`

## 问题

SVQuant 与 ResearchEngine 两仓目前只有人工启动脚本（`scripts/svquant.sh`），
没有自动化门禁和可回滚发布：

- 合并前没有统一测试入口，前端 11 个测试文件只有 6 个被脚本覆盖，后端刷新锁用例需要真实 PostgreSQL 才能通过；
- 部署步骤写在文档里手工执行，没有版本标识，回滚只能靠人工找旧代码；
- 两仓联调频繁，但没有「RE 先发、SVQuant 后发」的强制顺序。

## 选择

1. **流水线托管在 Gitee Go，执行在自建主机组**。仓库 `.workflow/*.yml` 只负责调用
   `scripts/ci/*.sh`，构建、测试、部署逻辑全部是普通 shell，可在 Jenkins、GitLab CI
   或本地一条命令复现（对齐 ADR-006「不把自动化强绑到平台私有能力」）。
2. **CI 只读、发布只认 tag**：PR 与 `master` 合并只跑测试和镜像构建校验；部署由
   `v*` tag 触发，部署版本号等于 Git tag。
3. **运行时用 Docker Compose**：`db`（PostgreSQL）、`backend`、`web`（Nginx 静态 +
   `/api` 反代）三个服务，端口只绑 `127.0.0.1`，TLS 由宿主机网关终止。
4. **失败回滚以镜像为粒度**：`deploy/.last-good.env` 记录上一组已验证镜像，
   冒烟失败即用旧镜像重新 `up`；发布前自动 `pg_dump` 到 `deploy/backups/`，
   数据库回滚保持人工（当前无迁移框架）。
5. **重活只在构建机执行**：开发机（16GB 内存、页面文件在机械盘、已多次因虚拟内存
   耗尽假死）只做编辑与秒级语法检查，`npm ci`、`vite build`、pytest、镜像构建全部
   交给构建机，避免本机再被压死。

选择自建主机组而非云构建的直接原因：Gitee Go 云构建的 Python 插件最高 3.9、
Node 插件最高 15，而本项目是 Python 3.13 + pandas 3.x + Vite 8（需 Node ≥ 20.19）；
账号级 500 分钟/月也不足以支撑两个仓库的日常门禁。

## 备选方案

1. **纯 Gitee Go 云构建**：零运维，但需要把后端降级到 Python 3.9 并重做前端工具链，
   与现有依赖冲突，成本高于自建构建机。
2. **自建 Jenkins**：最灵活、能挂长任务，但要额外维护 Jenkins 与插件；当前团队规模
   撑不起两套基础设施，主机组已能满足。
3. **镜像到 GitHub Actions**：生态最成熟，但 ADR-006 已确立 Gitee 为唯一事实来源，
   闭源代码不应镜像出境；仅发布审批过的开源组件时才考虑。
4. **继续手工部署**：短期成本最低，但无法回答「线上是哪个版本」和「怎么回滚」。

## 后果

正面后果：合并前有统一门禁（后端 pytest、前端构建+单测、镜像可构建）；发布可追溯、
可自动回滚；两仓流水线同构，联调顺序写进流程而不是口头约定。

负面后果：

- 构建机成为单点，需要自己维护 Docker、Python、Node 与磁盘；宕机时 CI 和发布同时不可用。
- 主机组要求构建机能访问部署网段，等于把一部分生产权限放在一台常驻机器上，需按最小权限管理。
- Gitee Go 免费额度仍是账号级 500 分钟/月，主机组任务同样计入；重度使用需评估加时包。
- 容器当前以 root 运行、无镜像漏洞扫描，这两项作为后续加固项登记在
  `../部署与运维/CI-CD.md` 的「当前边界」。

## 复审条件

1. 构建机连续故障影响交付，或团队出现第二套需要发布的系统；
2. E2E、性能测试、依赖扫描需要进入 PR 门禁，主机组排队时间不可接受；
3. 生产环境要求多可用区、蓝绿/金丝雀发布，单机 compose 无法满足；
4. Gitee Go 调整计费或主机组能力，成本高于自建 Jenkins。
