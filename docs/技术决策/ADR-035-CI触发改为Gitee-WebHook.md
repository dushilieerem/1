# ADR-035: CI 触发改为 Gitee WebHook

- 日期：2026-10-30
- 状态：已接受（取代 ADR-034 中「Gitee Go 主机组」的触发方式）
- 关联：`ADR-034`、`ADR-006`、`../部署与运维/CI-CD.md`、`../../deploy/webhook/`

## 问题

ADR-034 选择「Gitee Go + 自建主机组」，理由是云构建运行时太旧（Python 3.9 / Node 15）、
额度只有 500 分钟/月。实际落地时遇到硬阻塞：**该账号体系里没有「主机组」入口**——
仓库页只有流水线/构建历史/通用变量/发布记录，组织后台也找不到主机管理。

`shell@agent` 插件必须指定 `hostGroupID`，没有主机组这条流水线无法执行；而 Gitee Go
云构建又装不下 Python 3.13 + pandas 3.x + Vite 8。继续排查平台版本耗时且结果不可控。

## 选择

用 **Gitee WebHook + 自建接收器**替换 Gitee Go：

```
Gitee WebHook（Push / Tag Push，签名密钥）
  → 宿主机 Nginx /hooks/gitee
  → deploy/webhook/server.py（127.0.0.1:8788，验签 + 分类 + flock 串行）
  → scripts/ci/webhook-job.sh ci|deploy
  → scripts/ci/*.sh（原有测试、构建、部署、回滚脚本不变）
```

要点：

1. **平台只负责「通知」**，执行环境就是我们自己的服务器，运行时不再受平台限制；
2. 现有 `scripts/ci/` 全部复用，WebHook 只是多了一层「谁触发」；
3. 用签名密钥（`X-Gitee-Token` = HmacSHA256(timestamp+"\n"+secret)）而非明文密码，
   并校验时间戳偏差 ≤ 1 小时；
4. 接收器只监听 `127.0.0.1`，公网入口仅 Nginx 的一条 `location`；
5. `flock` 串行执行，避免 `git checkout` 与 `compose build` 互相踩；工作区有未提交改动时
   任务直接拒绝，不静默覆盖。

同时删除仓库里的 `.workflow/*.yml`（不再有主机组可用，留着只会在每次 push 时失败）。

## 备选方案

1. **继续找主机组入口**：可能是套餐/版本不具备该能力，或入口在私有化控制台；不确定性高，
   且即便找到，仍在平台侧维护一套与我们脚本重复的编排。
2. **改用 Gitee Go 云构建**：需要把后端降到 Python 3.9（与 pandas 3.x、现有类型标注冲突）、
   前端降到 Node 15（Vite 8 不支持），等于为了平台改写技术栈，否决。
3. **自建 Jenkins**：能力足够，但要多维护一套服务与插件；WebHook 接收器只有约 200 行、
   零第三方依赖，当前规模下性价比更高。
4. **服务器 cron 定时 `git pull`**：实现最省事，但无法区分 tag/分支、失败不可追溯，
   也失去了「推送即触发」的语义，否决。

## 后果

正面：触发链完全自主、可审计（每任务一份日志）、不占平台构建额度、不受平台运行时限制；
PR 合并后的 master 推送与 tag 发布都自动执行。

负面：

- 需要在公网暴露一个 WebHook 端点，安全边界从「平台托管」变成「自己守」——依赖签名校验、
  127.0.0.1 绑定、Nginx 限流三者共同保证；
- 触发与执行都在这台服务器上，它宕机时 CI 与发布同时不可用；
- 没有 Gitee 侧的构建状态回写，PR 页面看不到 CI 结果，需要看服务器日志（已列入边界）；
- 每个仓库要各自安装一个接收器实例（`--name`/`--port` 区分），运维面比平台方案略大。

## 复审条件

1. Gitee 开放主机组能力，且希望把 CI 结果回写到 PR 页面；
2. 接收器需要处理的事件类型显著增多（PR、评论、Issue），维护成本超过 Jenkins；
3. 出现多台构建机/多环境（测试、预发、生产），单机接收器无法满足隔离要求。
