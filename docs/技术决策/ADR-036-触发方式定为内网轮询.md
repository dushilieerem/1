# ADR-036: 触发方式定为内网轮询

- 日期：2026-10-30
- 状态：已接受（取代 ADR-035 的 WebHook 传输方式；[ADR-035](ADR-035-CI触发改为Gitee-WebHook.md) 的接收器保留给内网 Git 场景）
- 关联：`ADR-034`、`ADR-035`、`../部署与运维/CI-CD.md`、`../../scripts/ci/poll.sh`

## 问题

ADR-035 用 Gitee WebHook 触发，但落地时发现一个前提不成立：**公司网络没有公网入口**，
Gitee 的回调打不到内网服务器。同时 Gitee Go 的主机组在账号里也没有入口。两条路都断了：

- Gitee Go：没有 `hostGroupID` 可填，流水线无法执行；
- 公网 WebHook：没有可访问的入口地址，也无法（不应）为此开端口。

真实约束是：这是**公司内部 CI/CD**，代码托管在 Gitee，执行环境在内网，内网能出网、
外网进不来。

## 选择

用**内网主动轮询**替代被动回调：

```
systemd timer（默认 60s）
  → scripts/ci/poll.sh
       git fetch --prune --tags
       对比状态文件（master sha / 最新 v* tag）
       ├── 新 tag      → webhook-job.sh deploy refs/tags/<tag>
       └── master 变化 → webhook-job.sh ci master
  → scripts/ci/*.sh（原有测试、构建、部署、回滚，全部不变）
```

要点：

1. **方向反转**：从「外网推给我们」变成「我们定时去拉」，不需要任何入站端口；
2. **状态文件**记录上次见到的 master 与 tag，首次安装只建立基线，不会把历史版本重新部署一遍；
3. 失败后**不自动重试**（避免每分钟重跑一次失败构建），状态记录失败结果，人工修复后推新提交；
4. `flock` 防重叠；systemd `Type=oneshot` + `OnUnitActiveSec` 保证长任务不被下一轮打断；
5. ADR-035 的 WebHook 接收器不删除——将来若在内网自建 Gitea/裸 Git，回调走内网 IP
   即可，届时用它替换轮询，脚本层完全复用。

## 备选方案

1. **内网自建 Gitea + Actions**：体验最好（推送即触发、PR 门禁、构建历史），但要维护第二个
   代码托管服务，且与 ADR-006「Gitee 为唯一事实来源」冲突，需要额外定义镜像方向与权限。
   作为后续升级选项保留，不是当前阻塞项。
2. **纯 WebHook + 内网穿透**（frp/ngrok）：技术上可行，但把内网服务暴露到公网，需要额外的
   鉴权、限流与审计，违背「公司内部 CI/CD」的初衷，否决。
3. **Gitee Go 云构建**：运行时版本不满足（Python 3.9 / Node 15），否决。
4. **人工 `git pull` + 手动执行脚本**：零新增组件，但失去自动触发的意义，作为排障兜底保留。

## 后果

正面：完全内网闭环，无需公网入口；触发延迟上限等于轮询间隔（默认 60 秒）；
执行与日志都在自己的服务器上；状态与失败原因可查（`/var/lib/svquant/poll-state.env`）。

负面：

- **不是推送即触发**：最坏延迟一个间隔；对回滚这类要求秒级的场景不合适；
- **只能对 `master` 与 tag 做事**：PR 阶段没有检查结果，PR 门禁仍需人工或后续 Gitea；
- 轮询会周期性 `git fetch`，对 Gitee 有轻微请求压力（60 秒一次，可接受）；
- 状态文件是唯一"进度"来源，误删会把当前版本重新触发一次（可接受，`POLL_DRY_RUN=1` 可先看）。

## 复审条件

1. 需要 PR 门禁或推送即触发 → 评估内网 Gitea（Gitea Actions），并把 Gitee 设为 push mirror；
2. 公司开通可访问的内网入口（VPN/专线）→ 可切回 WebHook（接收器已就绪）；
3. 部署频率提高到分钟级、或需要多环境并行 → 轮询模型不再合适，转成真正的 CI 服务。
