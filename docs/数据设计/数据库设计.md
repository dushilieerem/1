## 1. 数据库信息

| 项 | 值 |
|---|---|
| 数据库类型 | PostgreSQL |
| 数据库名称 | 本地示例 `svquant`；实际以 `backend/.env` 的 `DATABASE_URL` 为准 |
| 连接入口 | `backend/services/core/db.py`（`get_conn`），各 store 调用 |
| schema | `public`（代码固定查询 `table_schema = 'public'`） |
| 字符集 | 待确认（代码未指定，跟随数据库实例默认） |
| 时区 | 待确认；代码时间列统一 `TIMESTAMPTZ`，写入用 `NOW()`（文档刷新脚本按 `Asia/Shanghai` 展示） |
| 迁移机制 | 无独立迁移工具。启动时 `backend/app/bootstrap.py` 依次调用各 store 的 `ensure_*_schema()`（幂等 `CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ADD COLUMN`/补列检查）；KnowledgeHub 用 `pg_advisory_lock` 串行化 DDL。是否迁移到正式 migration 工具见 §13 |

### 与外部数据存储的边界

| 存储 | 归属 | 说明 |
|---|---|---|
| SVQuant PostgreSQL（本文档） | SVQuant | 用户、社区、因子/策略资产与记录、资讯、AI 用量、审计、KnowledgeHub、RE 同步快照 |
| ResearchEngine 数据库/结果 SQLite | ResearchEngine | 行情 bars、回测明细结果、策略执行；SVQuant **不读取、不复制**（FEAT-031/032 边界） |
| marketdata 目录 | IFind 管道 → RE | SVQuant 不接触 |
| 文件系统 | SVQuant | 策略回测完整结果 blob（`backend/data/strategy_run_blobs/{user_id}/{run_id}.json.gz`，DB 只存摘要）；KH 附件二进制（`KH_ATTACHMENT_DIR`，DB 只存元数据） |
| 浏览器 localStorage | 前端 | AI 因子/策略生成历史暂未落库 |
| 临时文件 | SVQuant | 面板批任务进度 `backend/output/factor_dashboard/job.json`（重启丢失，非表） |
| 旧 `kb_*` 表 | 已删除 | 勿再建 |

## 3. ER 关系（text 图，均为逻辑关系或真实 FK，逐表标注）

```text
users ─┬─< user_follows >─ users            （自参照多对多；FK 真实，CHECK 禁自关注）
       ├─< user_watchlists ─< user_watchlist_symbols     （FK 真实，CASCADE）
       ├─< user_custom_factors                            （FK 真实）
       ├─< user_factor_libraries ─< user_library_factors  （FK 真实，双层 CASCADE）
       ├─< detect_projects ─< detect_runs                 （复合 FK (user_id,id)→(user_id,project_id)）
       ├─< strategy_projects ─< strategy_runs             （复合 FK 同上；完整结果在磁盘 blob）
       ├─< user_strategy_libraries ─< user_library_strategies
       ├─< posts ─┬─< post_comments ─< post_comments（parent_id 楼中楼，逻辑自关联）
       │          ├─< comment_votes
       │          ├─< post_votes
       │          ├─< post_favorites
       │          ├─< notifications
       │          └─< community_reports
       ├─< ai_usage
       └─(SET NULL) kh_collections / kh_documents / kh_files / kh_chats 的 created_by

kh_collections ─< kh_documents ─< kh_chunks
       │                    └──(逻辑关联，无 FK)── kh_attachments（文档附件元数据；
       │                                            二进制在 KH_ATTACHMENT_DIR）
       └─(SET NULL)─ kh_files
kh_chats ─< kh_conversations ─< kh_chat_messages
kh_chats ─< kh_chat_messages（chat_id 冗余直连）
kh_model_providers ←─(provider_key 逻辑关联)─ kh_default_models（role_key 唯一）

外部同步（非 FK）：
ResearchEngine GET /api/factors/catalog ──同步──▶ re_factor_catalog_snapshot（+ sync_log）
ResearchEngine GET /api/strategies ──────同步──▶ builtin_strategies（镜像）
```

## 5. 表结构

> 类型/NULL/默认值取自 DDL 原文；`◇` 标注该列由 `ALTER TABLE ADD COLUMN`（旧库补列）加入。

### A. 用户与权限

#### users（auth_store.py）

用途：账号与资料。主键：`id`。重要索引：`UNIQUE(username)`、`UNIQUE(email)`、`idx_users_status`。

| 字段 | 类型 | NULL | 默认值 | 说明 |
|---|---|---|---|---|
| id | BIGSERIAL | NO | 自增 | 主键 |
| username | TEXT | NO | | 登录名（3–32 位字母/数字/下划线）；公开主页 `/u/{username}` |
| email | TEXT | YES | | 邮箱（可空，唯一） |
| password_hash | TEXT | NO | | bcrypt 哈希，禁止明文（敏感） |
| role | TEXT | NO | `'user'` | CHECK：`user` / `admin` |
| status | TEXT | NO | `'active'` | CHECK：`active` / `disabled` |
| display_name | TEXT | YES | | 展示昵称（空则回退 username） |
| ai_quota_daily | INTEGER | NO | `200` | 每日 Agent 调用上限（按次，非 token） |
| created_at | TIMESTAMPTZ | NO | `NOW()` | 注册时间 |
| updated_at | TIMESTAMPTZ | NO | `NOW()` | 资料更新 |
| ◇avatar_url | TEXT | YES | | 头像 URL/dataURL（`_normalize_image` 校验并限长） |
| ◇cover_url | TEXT | YES | | 主页封面 |
| ◇headline | TEXT | YES | | 一句话简介 |
| ◇bio | TEXT | YES | | 关于我 |

#### user_follows（profile_store.py）

用途：关注关系。主键：`(follower_id, following_id)`。CHECK：`follower_id <> following_id`。

| 字段 | 类型 | NULL | 默认值 | 说明 |
|---|---|---|---|---|
| follower_id | BIGINT | NO | | 关注者 → `users.id`，ON DELETE CASCADE |
| following_id | BIGINT | NO | | 被关注者 → `users.id`，ON DELETE CASCADE |
| created_at | TIMESTAMPTZ | NO | `NOW()` | 关注时间 |

## 7. 数据关系

### 真实外键（DDL `REFERENCES`）

- `users` ← 所有资产表（`user_follows` 双列、`user_watchlists`、`user_custom_factors`、`user_factor_libraries`、`detect_projects`、`strategy_projects`、`user_strategy_libraries`、`post_comments.author_id`、`ai_usage` 等），多数 `ON DELETE CASCADE`。
- 例外：`posts.author_id`、`post_comments.author_id`、`strategy_plaza_items.author_id`、`community_reports.resolver_id` **无 CASCADE**（有内容/发布的用户删除会被外键拦截，防内容变孤儿——用户删除策略待确认）。
- KnowledgeHub 的 `created_by` 一律 `ON DELETE SET NULL`（用户删除不破坏知识库）。
- 复合外键：`detect_runs` / `strategy_runs` 的 `(user_id, project_id)` → 父表 `(user_id, id)`，从数据库层杜绝跨用户引用。
- 级联链：删用户 → 资产全清（帖/评论例外）；删项目 → 运行 CASCADE；删库 → 因子/策略条目 CASCADE；删帖 → 评论/投票/收藏/通知/举报 CASCADE；删 kh_collection → 文档 → 切块 CASCADE。

### 逻辑关系（无 FK，靠应用层维护）

- `kh_documents.attachment_file_id` → `kh_attachments.id`
- `kh_default_models.provider_key` → `kh_model_providers.provider_key`
- `kh_chats.collection_ids`（JSONB 数组）→ `kh_collections.id`
- `strategy_plaza_items.source_run_id` → `strategy_runs.id`（run 删除后广场快照自持）
- `user_library_strategies.source_run_id` → 研究 run（仅溯源，快照自持）
- `app_audit_logs.user_id` → `users.id`（故意无 FK，保留游客与历史快照）

### 关系基数

- 一对一：`users` ↔ 资料（同表扩展列，无独立 profile 表）。
- 一对多：用户 → 各资产表；库 → 条目；项目 → 运行；帖 → 评论/举报/通知；collection → 文档 → 切块；chat → conversation → message。
- 多对多（经中间表 + 复合主键实现防重复）：`users ↔ users`（user_follows）、`users ↔ posts`（post_votes / post_favorites / comment_votes）。
- 可再生缓存：`factor_dashboard_metrics`（可随时由 RE 重算覆盖）、`re_factor_catalog_snapshot`（重拉即得）、`builtin_strategies`（重同步即得）。
- 外部同步快照：RE 目录/策略列表 → `re_factor_catalog_snapshot` / `builtin_strategies`，以 `content_hash`/覆盖 upsert 保持**最终一致**（SVQuant 侧只读，写事实在 RE）。

## 9. 数据一致性

- **唯一性约束兜底归属**：`UNIQUE(user_id, name)` 贯穿因子库/策略库/自选分组；`UNIQUE(user_id, name)` + `UNIQUE(method_name)`（自定义因子）+ 双 UNIQUE（库条目）防重名；复合主键 `(user_id, id)` 保证业务键用户内唯一。
- **复合外键防越权**：detect_runs / strategy_runs 只能引用同 user 的项目（数据库层强制）。
- **CHECK 约束保枚举合法**：role/status、section/status、vote value、report reason/status、metrics 过滤位、plaza status。
- **幂等写入**：news `UNIQUE(raw_hash)` upsert；目录快照/内置镜像覆盖 upsert；`ensure_*_schema` 全部幂等；KH 重摄取按 `UNIQUE(document_id, ordinal)` 覆盖。
- **计数一致性**：view_count / vote 计数 / run_count 为直接 UPDATE，高并发允许瞬时偏差，不采用触发器汇总。
- **快照最终一致**：`re_factor_catalog_snapshot` 与 `builtin_strategies` 是 RE 事实的滞后镜像（hash 比对/覆盖式同步）；页面读快照，不实时打 RE。RE 侧数据变更与 SVQuant 快照刷新之间无事务（属跨系统最终一致）。
- **可再生 vs 事实**：`factor_dashboard_metrics` 可随时由 RE 重算覆盖（缓存语义）；`factor_dashboard_verifications` 与 `app_audit_logs` 是长期产品记录，不可重建；`builtin_strategies` 是目录镜像，**内置策略源码事实来源在 RE**，`source` 列仅为过渡期快照。
- **事务边界**：各 store 函数以 `get_conn()` 上下文为事务单元（写操作要么整提交要么回滚）；跨表级联依赖 FK ON DELETE，不写应用层补偿。

## 11. 备份与恢复

- **PostgreSQL 备份**：频率/方式（pg_dump/WAL 归档）/保存周期——**待确认**（代码与文档未定义）。

  4. KH 附件一致性：`kh_attachments` 每行对应的目录文件存在且 sha256 匹配；
  5. RE 快照可重建：触发 `re_factor_catalog` 预热与 `strategy/library/sync`。

| body（因子/策略源码） | user_custom_factors / user_library_factors / user_library_strategies | 中（用户私有资产） | 归属校验（`_require_*` / 复合 FK）；不跨用户返回 |
| 附件内容 | KH_ATTACHMENT_DIR + kh_documents.body / kh_files.body | 中 | 归属/角色门（KH 管理员语义，见模块文档） |
| token/secret 类 | （当前库内无独立 token 表；JWT 无状态） | — | 凭据只存 `.env`/密钥系统，不入库 |

### 脱敏与边界规则

1. 文档与日志样例禁止出现真实凭据；`refresh_database_docs.py` 的 `REDACT_KEYS`（password_hash/token/api_key/authorization/avatar_url/cover_url 等）统一打 `***`，长文本截断 120 字符。
2. 权限边界：所有私有资产查询带 `user_id` 条件或归属校验（越权 → 403/404）；管理员能力在 store 层按 role 判定。
3. 审计日志本身记录 path/ip/UA，属敏感聚合数据，仅管理员可查（`/api/admin/logs*`）。
4. 样例数据（seed_admin / seed_sample_posts / seed_sample_news）使用演示内容，不含真实凭据；`ADMIN_PASSWORD` 默认值仅限本地（生产必须覆盖）。
5. KH 模型供应商配置**含密钥，标注为敏感配置**：导出、日志、前端展示需脱敏（现状明文入库，密钥加密方案待确认）。

10. **kh_model_providers.api_key 加密存储**方案（当前明文）。
11. **dashboard 批任务进度**（`backend/output/factor_dashboard/job.json` 临时文件）是否入库化（待 RE 任务 API 接管后退役，随 FEAT-030）。
12. 产品数据量级（用户数、日发帖/回测次数）以校准容量规划。
