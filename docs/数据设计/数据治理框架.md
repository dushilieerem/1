# SVQuant / ResearchEngine 数据治理框架

> 编写日期：2026-10-30
> 范围：行情 Parquet、SVQuant PostgreSQL 业务库、KnowledgeHub 知识库，以及后续财报 / 公告 / 新闻 / 研报
> 性质：设计建议，不改代码

---

## 0. 先给判断

**存储本身没有问题，问题是同一份数据在三套系统里有三种说法。**

- 所有权其实已经清楚：`IFind` 采集发布 → `ResearchEngine` 只读消费并计算 → `SVQuant` 产品层。这个边界是对的，不要推翻。
- 缺的不是数据库，而是**运行时的治理面**：数据目录、血缘、契约校验、文档资产模型、生命周期与权限。这五项目前一项都没有。
- 未来财报/新闻/研报进来后，真正会失控的是**文档类数据**：现在 `news_items` 只是一个带 FIFO 裁剪的资讯流，KnowledgeHub 只是手动上传的文档库，两者不通，也没有原文归档和版本。

**一句话方案**：三套存储继续用，但在上面加一层「契约 + 目录 + 血缘 + 质量 + 权限」，并且把文档类数据单独建成「原始件 + 元数据 + 检索索引」三层。

## 1. 当前基线（事实）

| 系统 | 归属 | 存储 | 内容 | 现状 |
|---|---|---|---|---|
| IFind | 数据生产方 | 本地 raw + `marketdata/` | 采集、解析、质量、发布、备份 | 已有 release + manifest + quality_report，流程完整 |
| ResearchEngine | 研究计算方 | 只读 `marketdata/` + 结果 SQLite | 因子/策略回测、行情查询 | 启动校验 manifest、60 秒热重载 |
| SVQuant backend | 产品层 | PostgreSQL 47 张表 + 本地 blob | 用户、社区、新闻、自选、因子/策略配置、模拟盘、审计 | 手写 DDL，无 migration 工具 |
| KnowledgeHub | SVQuant 内模块 | 同库 10 张 `kh_*` 表 + 附件目录 | 文档、切块、向量、对话 | 向量存 JSONB，检索全表扫描 |
| invest-api | 独立 MVP | SQLite `invest.db` | 演示行情、组合、新闻 | 与主库完全分离 |

**已经做得好的**：

- `marketdata` 不可变 release、manifest 带 sha256、RE 启动校验版本、原子切换。
- FEAT-010 有字段字典与数据清单；FEAT-025 有免费源字段契约与状态枚举。
- 模拟盘结算已经带 `data_release_id`，这是全系统唯一一处把「数据版本」写进业务事实的地方。

**已经开始失控的**（同一件事有多种口径）：

| 问题 | 表现 |
|---|---|
| 字段命名三套 | `total_mv/float_mv/pe/pb`、`total_market_cap/pe_lar/pb_mrq`、实际 release 的 `current_mv/pe_ttm/pb_mrq` |
| manifest 三种 | FEAT-010、FEAT-024、FEAT-025 各写一套 schema |
| 状态枚举两套 | `ready/blocked/deprecated` vs `ready/partial/blocked/legacy` |
| release 命名三种 | `ifind-sync-*`、`2026.07.0`、`free-basic-status-*` |
| 日历三种 | `calendar_all_a` 长表、`trading_calendar` 宽表、`SH/SZ/BJ.parquet` |
| 指数目录两种 | `benchmark/index_*` 与 `index/index_price` / `index/index_weights` |
| 文档快照漂移 | `09-current-data-fields.md` 仍是 406 天基线，实际已 2,617 天 |
| 停牌来源四种 | `listed_status` 派生、BaoStock、`up_and_down_status`、当前不提供 |

**结论：治理的第一件事不是建新系统，是把这 8 处口径收敛成唯一版本。**

## 2. 十条统一基线（先做，2 周内可完成）

| # | 项 | 唯一口径 |

## 3. 分层模型

```text
L0 原始层 Raw        供应商原始响应、公告/新闻/研报原件（PDF/HTML）、抓取日志
L1 标准层 Normalized 统一字段、统一单位、统一证券主键的结构化数据
L2 时点层 PIT        去重、实体对齐、公告日可见性、财报重述版本
L3 派生层 Derived    因子、指标、标签、摘要、向量
L4 服务层 Serving    RE API、SVQuant API、知识库检索、缓存

横切：目录 Catalog / 血缘 Lineage / 质量 Quality / 权限 ACL / 审计 Audit
```

| 层 | 允许存放 | 不允许 |
|---|---|---|
| L0 | 原始字节，永不修改 | 业务逻辑、字段重命名 |
| L1 | Parquet 面板、PG 业务表、文档元数据 | 直接供回测的时点逻辑 |
| L2 | 加 `pub_date`/`available_at` 的版本 | 用最新快照回填历史 |
| L3 | 可重算的派生结果 | 成为唯一事实来源 |
| L4 | API、索引、缓存 | 直接改 L0–L2 |

**关键规则：L1 可以被重建，L0 不能。** 任何 L1 数据都必须能从 L0 + 代码 + 契约重跑出来。

## 4. 存储选型矩阵

不要按「系统」选存储，按「数据形状 + 访问模式」选。

| 数据 | 形状 | 存储 | 理由 |
|---|---|---|---|
| 行情、估值、状态 | 日期 × 证券宽表 | **Parquet release** | 列式、不可变、按字段读、适合长历史 |
| 财务三表 | 报告期长表 | **Parquet** | 体积小、只读、按 `pub_date` 做 PIT |
| 分红 / 回购 / 股本事件 | 事件长表 | **Parquet** | 追加式、只读、需要精确日期 |
| 因子 / 指标 / 特征 | 日期 × 证券宽表 | **Parquet** | 可重算，避免进业务库 |
| 文档元数据、证券关联 | 关系表 | **PostgreSQL** | 需要事务、外键、联表 |
| 公告 / 新闻 / 研报原件 | 大对象 | **对象存储**（MinIO/S3）或共享文件系统 | 体积大、不可变、按哈希寻址 |
| 文档切块与向量 | 行数大、向量检索 | **PostgreSQL + pgvector** | 一个库解决元数据与向量，避免双写 |
| 业务事实（用户、组合、订单、模拟盘） | 事务 | **PostgreSQL** | 强一致、并发、约束 |
| 回测结果 | 大 JSON/表格 | **对象存储 + PG 索引** | 结果大、只读、按版本引用 |
| 审计 / 用量 | 追加日志 | **PostgreSQL append-only** | 需要查询与保留策略 |
| 缓存 / 会话 | 临时 | 进程内或文件 | 可再生，不进治理范围 |

**建议新增两样基础设施**（不需要现在全上）：

1. **对象存储**（MinIO 即可）：所有原始文档、PDF、回测结果放这里，按 `sha256` 寻址。
2. **pgvector**：KnowledgeHub 迁移到真实向量索引，别再用 JSONB 全表扫。

## 5. 元数据与数据目录

### 5.1 契约即代码

建一个目录（可放在 SVQuant `docs/数据契约/` 或独立仓库）：

```text
data-contracts/
├── market/panel.yaml
├── market/financials.yaml
├── documents/announcement.yaml
├── documents/news.yaml
├── documents/research.yaml
└── business/paper_trading.yaml
```

每个契约至少包含：

```yaml
dataset_id: market.financials.income
owner: data-platform
zone: L2
grain: [thscode, end_date, report_type]
keys: [thscode, end_date, report_type]
storage_uri: marketdata/financials/income.parquet
schema_version: 1
fields:
  - name: np_parent_company_owners
    dtype: float64
    unit: CNY
    pit: {event_time: end_date, publish_time: pub_date}
    source: [akshare.eastmoney]
    status: ready
freshness: {sla: "T+1 18:00"}
license: internal_only
retention: permanent
consumers: [research-engine]
```

**契约由 CI 校验**（schema、字段唯一、枚举合法、PIT 规则完整），发布时与数据一起进 manifest。

### 5.2 目录表（PostgreSQL `meta` schema）

在 SVQuant 主库新建 `meta` schema，作为可查询的目录（只读同步，不承载事实）：

| 表 | 用途 |
|---|---|
| `meta.dataset` | 数据集：id、owner、zone、storage_uri、grain、keys、覆盖期、SLA、license、retention |
| `meta.field` | 字段：dataset_id、名称、类型、单位、口径、PIT 规则、source、status |
| `meta.dataset_version` | 版本：version、manifest_uri、sha256、rows、created_at、parent_version |
| `meta.run` | 每次采集/构建：run_id、dataset、输入版本、代码 commit、参数、状态、行数、耗时 |
| `meta.lineage_edge` | 血缘：from_dataset/version → to_dataset/version、run_id、字段映射 |
| `meta.quality_result` | 质量：run_id、检查项、阈值、结果、指标 |
| `meta.license` | 授权：source、允许用途、再分发、缓存期限 |
| `meta.asset_acl` | 权限：dataset_id、role、read/write |

**生成方式**：IFind/RE 发布后把 `manifest` 与 `quality_report` 推到 `meta`；SVQuant 提供只读 API。不要让三边各维护一份目录。

### 5.3 目录必须能回答的六个问题

1. 这份数据从哪来、许可允许做什么？
2. 覆盖到哪一天、是否完整？
3. 字段口径是什么、PIT 用哪个时间？
4. 当前版本是什么、上一版是什么、能否回滚？
5. 谁在用、改它会影响哪些因子/回测？
6. 质量过没过、最近一次失败是什么？

## 6. 时间语义（财报/新闻治理的核心）

每条记录至少三个时间：

| 时间 | 含义 | 用途 |
|---|---|---|
| `event_time` | 报告期 / 事件发生时间 | 分析、分组 |
| `publish_time` | 公告日 / 发布时间 | **回测唯一可用时间** |
| `ingest_time` | 入库时间 | 运维、补数判断 |

**硬规则**：

1. 回测只允许按 `publish_time <= asof` 取数，禁止用 `event_time` 或 `ingest_time`。
2. 财报重述保留版本：`version`、`is_latest`、`supersedes`，不覆盖原值。
3. 新闻/研报用 `published_at`（源）与 `first_seen_at`（我们第一次抓到）；历史补采时必须标记 `backfilled=true`。
4. 文档同一内容多次发布，用内容哈希去重，但保留所有版本与来源。
5. 任何「用最新快照回填历史」的操作必须被质量门禁阻断。

## 7. 文档资产治理（财报 / 公告 / 新闻 / 研报）

### 7.1 一条统一管道

```text
源登记 → 抓取原始件 → 解析文本 → 去重 → 实体对齐 → 切块/向量 → 建索引版本
  meta.license   L0 对象存储   L1 doc_document   L1 doc_hash   L2 doc_security   L3 doc_chunk
```

### 7.2 源登记

每个来源一条记录：名称、URL、许可、允许用途、抓取频率、限流、保留期、是否可再分发。没有登记的来源不得入库。

### 7.3 原始件存储

```text
raw/<source>/<yyyy>/<mm>/<dd>/<sha256>.<ext>
raw/<source>/<yyyy>/<mm>/<dd>/<sha256>.json   # 抓取元数据：URL、时间、状态码、headers
```

原件不可修改；解析失败可以重跑，原件不能丢。

### 7.4 文档核心表（统一 news / announcement / research / file）

| 表 | 关键字段 |
|---|---|
| `doc_source` | source_id、name、license、rate_limit、retention |
| `doc_document` | doc_id、source_id、doc_type、title、publisher、published_at、first_seen_at、content_hash、url、lang、license、status |
| `doc_version` | doc_id、version、content_hash、raw_uri、parsed_uri、supersedes、created_at |
| `doc_security` | doc_id、thscode、method（announcement_meta / nlp / manual）、confidence |
| `doc_chunk` | doc_id、version、ordinal、text、chunk_policy_version、embedding_model、embedding_version、embedding vector |
| `doc_fetch_log` | source_id、url、status、fetched_at、latency、error |

`news_items` 可以保留为「资讯流视图」，但**长期档案必须在 `doc_document`**；现有的 FIFO 裁剪只能清理视图，不能删原始件。

### 7.5 去重与实体对齐

- 精确去重：规范化 URL + `content_hash`。
- 近似去重：SimHash/MinHash，命中后标记 `duplicate_of`，不删除。
- 证券关联：公告元数据优先（公告代码/简称）；新闻用标题+正文实体识别，记录方法与置信度；名称变更走 `security_master` 别名表。
- 行业/主题标签作为单独表，带 taxonomy 版本。

### 7.6 向量与检索

- 从 `kh_chunks.meta->'embedding'` 迁移到 `doc_chunk.embedding vector(1024)` + HNSW 索引。
- 索引带版本：`index_version`、`chunk_policy_version`、`embedding_model`；重建时写新表再切换，不原地改。
- 检索结果必须返回 `doc_id + version + chunk_id`，保证可引用、可复现。

### 7.7 三类文档的差异

| 类型 | 保留 | 权限 | 备注 |
|---|---|---|---|
| 公告 / 财报 | 永久 | 内部 | 与财务结构化数据用 `announcement_id` 关联 |
| 新闻 | 原件永久，热索引 2 年 | 内部 | 关注时效与去重 |
| 研报 | 按许可 | 严格 ACL | 可能禁止再分发，只存元数据+摘录 |

## 8. 质量与契约

### 8.1 分层门禁

| 层 | 检查 |
|---|---|
| L0 | 请求成功、内容非空、哈希可算、来源已登记 |
| L1 | schema、类型、键唯一、日期升序、非空率、单位 |
| L2 | `publish_time >= event_time`、PIT 无未来、证券存在、去重 |
| L3 | 可重算（同输入同哈希）、与上一版差异可解释 |
| L4 | API 契约测试、字段投影、缓存失效 |

### 8.2 跨源对账

换源（iFinD → 免费源）必须出重叠期差异报告：按字段、按日期、按分位数，记录在 `meta.quality_result`。**只报告，不自动覆盖。**

### 8.3 质量看板

从 `meta.quality_result` 出三个视图：当前版本是否健康、最近 7 天失败项、字段覆盖率趋势。SVQuant 前端可展示，RE 启动也可读。

## 9. 血缘与影响分析

### 9.1 最小可用

| 动作 | 落点 |
|---|---|
| 每次采集/构建 | `meta.run` + `meta.lineage_edge` |
| 每个回测 | `strategy_runs.data_release_id`（目前只有模拟盘有） |
| 每个因子面板结果 | `factor_dashboard_metrics.data_release_id` |
| 每次模拟盘结算 | 已有 `paper_settlements.data_release_id`，保持 |

### 9.2 能回答的问题

- 这个回测用的是哪一版行情、哪一版财务？
- 升级到新 release 后，哪些因子值变了、哪些策略结果变了？
- 某个源字段异常，会影响哪些数据集和策略？

### 9.3 实现方式

不要上完整 OpenLineage。先用两张表 + 发布时写入即可：`meta.run`（谁在什么时候用什么输入产出了什么）和 `meta.lineage_edge`（数据集版本之间的有向边）。字段级血缘可先只记录 `field_map` JSON。

## 10. 生命周期、权限、合规

### 10.1 保留策略

| 数据 | 保留 |
|---|---|
| 行情 / 财务 / 事件 | 永久；release 保留最近 N 版 + 每季度归档一版 |
| 原始文档 | 永久（对象存储） |
| 新闻热索引 | 2 年，之后归档 |
| 回测结果 | 按用户/项目保留，超期归档到对象存储 |
| 审计 | 按合规要求（当前未定，建议 ≥ 2 年） |
| 临时缓存 | 可随时删除 |

### 10.2 权限模型

- 角色：`producer`（写 L0/L1）、`researcher`（读 L1–L3）、`product`（读 L4）、`admin`。
- 数据集级 ACL，字段级暂不做。
- 许可作为 ACL 的一个维度：`internal_only`、`no_redistribution`、`pii`。
- 凭据只放在采集服务，产品后端不持有供应商 key；KH 的 `api_key` 明文需要加密。

### 10.3 审计

现有 `app_audit_logs` 只记 HTTP 操作。新增数据访问审计：谁在什么时候读了哪个数据集/哪个文档版本。至少覆盖研报与敏感附件。

## 11. 调度与运行

现状：进程内 daemon 线程 + 外部 cron + 手动脚本，没有 DAG、重试、任务注册表。

**不建议立刻上 Airflow。** 先做到四件事：

1. **任务注册表**：`meta.job`（名称、数据集、依赖、cron、超时、重试）。
2. **幂等**：每个任务有 `run_key`（数据集 + 区间 + 参数哈希），重复运行不产生重复数据。
3. **断点与重试**：raw 缓存命中即跳过；失败只重跑缺口。
4. **统一入口**：每个数据集一个 `run.py`，参数固定为 `--start/--end/--mode`。

等任务数超过 ~30 个或出现跨天依赖时，再引入 Prefect/Dagster。

## 12. 组织与流程

| 角色 | 责任 |
|---|---|
| 数据 owner（按域） | 行情、财务、文档、业务各一人，对契约和 SLA 负责 |
| 数据 steward | 质量告警、补数、对账报告 |
| 消费方代表 | 研究、产品，参与契约变更评审 |

流程：

- 新数据集先写契约，评审通过才开发。
- 契约变更走 RFC，必须给出兼容期与迁移方案。
- 发布失败/数据事故有 runbook：定位版本 → 回滚 → 出影响报告。
- 数据集废弃先标 `lifecycle: deprecated`，保留一个发布周期后再删。

## 13. 落地路线

### 第 1 期（2–3 周）：止血与统一

- 收敛 §1 的 8 处口径，指定唯一来源。
- `09-current-data-fields.md` 改为生成器产出，纳入 CI 漂移检查。
- manifest 升到 `schema_version: 3`，加字段级来源。
- 建 `meta` schema 与目录同步任务。
- 回测结果写 `data_release_id`。
- 修 KH 明文 key、默认匿名 admin。

### 第 2 期（4–6 周）：文档资产

- 部署对象存储；原始件按哈希落盘。
- 建 `doc_*` 表，新闻先双写，再迁历史。
- KH 向量迁 pgvector，检索走索引版本。
- 公告先接（与财务数据关联），研报只存元数据。

### 第 3 期（6–8 周）：血缘、质量、生命周期

- `meta.run` / `lineage_edge` 全链路打通。
- 质量看板与发布阻断。
- ACL、许可、保留策略落地。
- 数据访问审计。
