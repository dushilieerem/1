# 用户与权限模块 流程设计

## 1. 流程说明

覆盖注册、登录、请求鉴权、资料与关注、审计日志五条流程。

## 2. 参与模块

| 参与者 | 职责 |
|---|---|
| frontend | 登录/注册表单、Token 存储、401 跳转 |
| `routers/auth.py` | 注册/登录/资料/关注入口 |
| `routers/admin_logs.py` | 审计日志查询/清理入口（管理员） |
| `auth_store` | 密码、JWT、用户查询 |
| `profile_store` | 资料、关注、用户主页聚合 |
| `audit_log_store` | 审计写入/查询/清理 |
| `app/main.py` 中间件 | 自动审计写操作与错误 |
| PostgreSQL | users / user_follows / app_audit_logs |

## 3. 正常流程

### 注册

```text
前端提交 username/password(/email/display_name)
  → 校验非空与格式 → hash_password
  → INSERT users（role=user, status=active, ai_quota_daily=200）
  → write_audit("auth.register")
  → 返回 token + user
```

### 登录

```text
前端提交 username/password
  → get_user_by_username → verify_password
  → issue_token（JWT：uid/role，JWT_EXPIRE_DAYS 天）
  → write_audit（登录由中间件记录：失败必记；成功登录走路由显式记录，中间件跳过避免重复）
  → 返回 {access_token, token_type, user}
```

## 4. 时序流程（受保护请求鉴权）

```text
浏览器 -> Router：请求 + Authorization: Bearer <JWT>
Router -> deps.require_user：依赖注入
deps -> auth_store.user_from_authorization：解码 JWT
auth_store -> PostgreSQL：SELECT users（校验存在与 status=active）
auth_store --> deps：用户字典（或 None）
alt 用户无效
  deps --> Router：HTTPException 401 {"error":"未登录"}
end
Router -> Service：携带 user 执行业务
Service -> PostgreSQL：按 user.id（或 resolve_db_user_id）过滤读写
Service --> Router：结果
Router --> 浏览器：200 / 业务响应
中间件 finally -> audit_log_store：写操作或错误 → INSERT app_audit_logs（含 X-Request-Id）
```

管理员接口把 `require_user` 换为 `require_admin`（role != "admin" → 403）。

## 5. 异常流程

### 异常 A：凭据错误

- 注册：用户名重复/参数非法 → 400，写 `auth.register_failed` 审计。
- 登录：密码错误/用户不存在 → 401（审计必记）。

### 异常 B：身份失效

- JWT 过期/非法 → `user_from_authorization` 返回 None → 401；前端引导重新登录。
- 用户被禁用（status=disabled）→ 同样 401。

### 异常 C：权限不足

- 非管理员访问 `/api/admin/logs*` 或 Agent 用量管理 → 403"需要管理员权限"。

### 异常 D：审计写入失败

- 中间件 finally 中吞异常（不放大业务错误）；管理端查询时该条缺失，可接受（日志兜底）。

## 6. 状态流转

```text
用户：registered(active) ──禁用──▶ disabled ──启用──▶ active
关注关系：无 ──follow──▶ following ──unfollow──▶ 无（幂等重复操作以数据库约束/存在性判断兜底）
审计记录：写入即终态（仅管理端查询与按天清理）
```

## 7. 并发处理

- username 唯一约束防重复注册；并发同名校验由数据库兜底（后者 400）。
- `user_follows` 联合主键防重复关注；自关注由 CHECK 约束拒绝。
- 审计 INSERT 并发安全（自增主键 + X-Request-Id 关联）。

## 8. 幂等设计

- `DELETE follow` 重复调用返回幂等结果（不存在不报错，以实现为准）。
- 日志 purge 按条件清理，重复执行安全。
- 注册/登录天然非幂等（各自写审计），依赖前端防重复提交。

## 9. 超时和重试

- 全部为本地数据库操作，无外部超时；连接失败随 `get_conn` 直接抛错。
- 无自动重试；登录失败由用户重试（限流待确认）。
