## 3. 八个必答问题

### Q1 试验次数 K 与 `t*(K)` 门槛在哪算、被谁调用、有没有第二条绕过路径？

**公式**：`metrics.threshold(k, alpha=0.05) = NormalDist().inv_cdf(1 - 0.05/(2k)) = Φ⁻¹(1−0.025/K)`，`k` 必须为 ≥1 的整数（`backend/services/quant_factor/metrics.py:17-23`）。

**K 不落库、每次重算**：`ledger.current_k(trials, primary_holding_period)` 对台账行调用 `counts_toward_k` 求和（`ledger.py:148-152`）。计数规则（`ledger.py:116-138`）：
- 排除 `diagnostic/edit/rerun/sealed` kind、`rerun_of`、rerun outcome；
- `passed/failed` 必计；
- `error/timeout/cancelled` 仅当 `returned_metrics` 为真才计；
- 登记了主持有期时，持有期不一致的不计；缺持有期直接抛错（fail-closed）；
- 未知 outcome 抛错，不静默计入/排除。

**台账追加**：`ledger.append_trial`（`ledger.py:668-749`）在事务内取 `(9106,uid)`/`(9111,uid)` 咨询锁，`trial_no = MAX+1`，`rerun_of` 由服务端比较 implementation_hash/release/view/parameters 派生；`returned_metrics` 由 `result_summary` 派生；复现字段只从 topic 锁读取，不接受客户端提供。DB 有 `UNIQUE(user,org,project,trial_no)`（`0011:83`）和 UPDATE/DELETE 触发器（`0011:112-131`）。

**生产调用路径**：

| 路径 | 位置 | 用的 K |
|---|---|---|
| 研发 gate | `service._gate_k:206-213` → `service.run:292` | `current_k + 1`（本次检验计入后） |
| 验证/legacy | `service._gate_k:213` | `current_k`（V5 `validate` 被 195-196 拒绝，实际不走） |
| 候选创建预算 | `service.create:126-131` | `current_k + _reserved_development` |
| 封存前复核研发 | `sealed._check_new:80-83` | `current_k` |
| 封存结果判定 | `sealed._run_once:227-234` | 结果时的 `current_k` |
| 复核页/决定 | `review._ledger_context:119-135`、`review.record:192-198` | `current_k`；NW t 与当前门槛比较 |
| 资产批准复核 | `assets.validate_evidence:68-77` | `current_k`，重新算 dev+sealed gate |
| 台账/门槛接口 | `ledger.ledger_view:652-663`、`threshold_view:752-759`、router `257-260` | `current_k`；`threshold(max(k,1))`；调用者可传任意 k |
| F0 上下文 | `f0_agent._context:136-138,161` | `t_critical=threshold(max(k,1))`、`next_new_trial_threshold=threshold(k+1)` |
| 自动迭代预检 | `iterations.start:80-81` | **候选数** `maxTrials - len(candidates)`，不是 K |
| autonomy family | `autonomy_contract.trial_permission:71-86` | 自己的 `family_k`；生产未接线 |

**第二条/绕过路径**（均需在改动前知道）：
1. `policy.evaluate:100-104` 对 `k=None/0/非 int` 静默按 `1`，并把 `k_used` 记为 1。当前生产调用都显式传 K，但这是潜在的“最宽松”入口。
2. `service._gate_k:211` 在无 topic 时固定返回 1（legacy 路径）。
3. `iterations.start:80` 用候选数做预算预检；真正的 K 预算仍在 `service.create`，所以不会降低统计门槛，但可能先放行后失败。
4. `autonomy_contract` 的 `family_k`/`trial_permission` 有独立语义，生产未接线（grep 仅测试）。
5. **外部失败/取消未落台账**：`service.run:278-281` 在 `failed/cancelled` 时直接 `store.update` 并 return，未调用 `_append_development_trial`。若外部失败返回了部分指标，按规则应计入 K，但实际不会；K 会偏小，门槛偏松。`_append_development_trial` 本身也是 best-effort，异常只写 `ledger_append_failed`（`service.py:323-326`）。

### Q2 “封存每个候选只能用一次”靠什么保证？并发会不会重复？失败能否重试？

**DB 约束**：`quant_factor_sealed_validations` 有 `UNIQUE (candidate_id)`（`backend/migrations/0011_quant_factor_v5_ledger.sql:86-110`，唯一键在 :109）。这是最终兜底。

**代码/锁**：`sealed._locked:39-52` 在事务内依次取 `pg_advisory_xact_lock(9106,uid)`、topic-start 咨询锁、project `FOR UPDATE`、candidate `FOR UPDATE`，并尝试对已有 seal 行 `FOR UPDATE`。`sealed.request:100-121`：
- 已有 seal 行：直接返回（replay），不重新检查预算/状态（`:103-107`）；
- 无 seal 行：`_check_new`（研发达标、未登记、snapshot 未变、无研究侧样本外暴露、研发按当前 K 仍达标、查重完整、验证区间/数据身份一致），再 `COUNT(*)` 该 user+org+topic 的封存行，`>= topic.max_sealed` 拒绝（`:113-114`），然后 plain INSERT（`:116-120`）。

**并发**：同一用户/机构/候选的第二个请求会在 `sealed._locked` 的咨询锁/候选行锁上等待；第一个提交后它看到已有行并 replay。若有人绕过锁，`UNIQUE(candidate_id)` 会拒绝，但 plain INSERT 不会被 `invoke` 转成 409，而是未处理 DB 错误 → 500（推断；正常路径不会走到）。

**worker**：`sealed.run:161-165` 用 `pg_try_advisory_xact_lock('quant-factor-sealed-worker:{uid}:{org}:{sid}')` 保证单领；`_run_once` 在提交前先持久化 `submission_started=True`（`:192-193`），丢失响应时后续只报“尚未确认，不会重复计算”（`:177-178`）。

**失败/重试**：
- 外部 `failed`：`_run_once:220-222` 写 `status='error'`、`confirmation='failed'`；`cancelled` 写 `status='cancelled'`、`confirmation='cancelled'`；
- gate 不通过：`:234` 写 `status='failed'`；
- 这些终态下 `_persist` 拒绝再写（`:138`），`request` 只会 replay 原行；**同一候选不能重试**；
- `failed/error/cancelled` 行都计入 `topic.max_sealed`（`:113-114` 无状态过滤），失败会消耗课题额度；
- 预分发失败/队列恢复的 `error + confirmation='not_submitted'` 不会被 `sealed.request` 重新调度（`:106` 的条件只接受 `error` 且有 `run_id` 且 `confirmation='pending'`）；是否有运维重试 API **未确认**，推断会 stranded 且仍占额度。

**死代码**：`ledger.sealed_request_error/can_request_sealed`（`ledger.py:189-209`）按 trial 的 `candidate_id` 判断“一候选一次”，但 `quant_factor_trials` 没有 `candidate_id` 列，且生产无调用；实际规则只在 `sealed.py` + DB 唯一键。

**旧文档“第二次 409”**：源码的 replay 是返回现有行（200），不是 409；DB 唯一键是兜底。见 §6。

### Q3 “批准研究用途 + 资产登记”是不是同一个事务？失败会不会半提交？谁有权限？

**结论**：在 `assets.approve` 内部是同一连接、同一事务、同一条 UPDATE；跨工作流步骤（archive → review request → 迭代状态）是分开的事务，可能部分提交。

**路径**：
- 研究员归档：`POST /candidates/{cid}/archive` → `service.archive:443-452`，只写 `archive` 的 `purpose/note/snapshot_hash/approved=False/sealed=False`，**不创建资产**。
- 正式提交：`POST /candidates/{cid}/submit` → `quant_factor_workflow.py:38-41` 固定 409；没有 `service.submit`（grep 无 `def submit`）。
- 申请复核：`POST /candidates/{cid}/review-request` → `review.request_review:52-73`；`research_admission` 会先 `assets.eligibility(..., for_submission=True)`（`:65-67`），再写 `archive.review.status='requested'`。
- 领取：`POST /reviews/{cid}/claim` → `review.claim:99-111`，写 `assigned_to/assigned_at`。
- 批准/登记：`POST /reviews/{cid}`，`decision='approve_research_and_register'`（router `104-110`）→ `assets.approve:113-163`。

**事务/原子性**：`assets.approve` 的 `with get_conn() as c:`（`:121`）中依次锁 actor/ topic/project/candidate（`:126-131`），`ensure_reviewer`/`ensure_assigned`（`:132-134`），`eligibility(row,c)`（`:140`）重新读 topics/trials/sealed/project 并重算 dev/sealed gate（`validate_evidence:41-96`），构造 asset、`registration_hash=digest(asset)`（`:158`），最后**一次** `UPDATE quant_factor_candidates SET archive=..., events=...` 同时写入 `review`、`approved=True`、`research_asset`（`:159-162`）。`get_conn` 正常退出才 commit，异常回滚（`services/core/db.py:175-187`）。因此 `approve` 内部**不会半提交**。`return serialize(asset,org,full=True)` 在事务外（`:163`）；若序列化失败，资产已提交但客户端看到错误（推断，低概率）。

**权限**：
- `approve/record/claim/f5` 路由均为 `require_quant_reviewer`（`quant_factor_workflow.py:94-110,405-408`；`deps.py:88-94`），只有 `can_review`（`quant_reviewer`）可进；
- `assets.approve` 服务层再调 `ensure_reviewer`（作者自审拒绝，`review.py:94-97`）和 `ensure_assigned`（必须已领取，`review.py:113-117`）；
- 所有查询带 `org_id`（`assets.py:124,127,131`；`review.py:102,183`；`sealed.py:45-51`）；
- manager（`can_manage`）没有批准路由权限；`require_quant_reviewer` 只认 `can_review`（`deps.py:88-94`）。
- **代码层限制**：`assets.approve` 本身不重查调用者角色，只查“不是作者 + 已指派”；未来若有别的调用者直接调服务层，可能绕过路由角色（推断）。

**半提交/风险**：
- `approve` **不校验 topic.status == active**；暂停/归档课题的候选在复核证据齐全时仍可被批准（源码未见检查；`request_review` 也不检查 topic status）。
- `approve` **不更新 branch/topic/candidate.status**；`ledger_view` 的分支显示仍按 `branch.status + sealed.status`，在没有 `approved` 分支状态时仍显示“封存通过，待提交”（`ledger.py:616-627`；推断，未做浏览器复核）。
- 跨步骤：`iterations.submit_research:161-176` 先 `service.archive`（独立事务）再 `review.request_review`（另一事务），后者失败会留下已归档但未请求复核；`f0_agent:513-523` 先保存 passed seal，再单独请求复核，失败会留下 passed seal 无 review item。
- 另一条“登记”路径：`POST /candidates/{cid}/register` → `service.register_asset:454-471`，把代码复制到用户因子库（`add_library_factor`），再更新 candidate archive；这不是正式研究资产，且两次写入可能一个成功一个失败（`add_library_factor` 与 candidate UPDATE 不在同一 `with` 的原子保证内；推断）。

### Q4 F0 决策：动作白名单在哪定义/拦截？非法动作怎么处理？检查点在哪？

## 5. 风险清单（改之前必须知道什么）

### 5.1 K / 门槛 / 台账可信度
1. **外部失败/取消未落台账**：`service.run:278-281` 在 `failed/cancelled` 直接 return，`_append_development_trial` 未执行；若外部返回了部分指标，按规则应计 K，实际不计 → 门槛偏松（`service.py:323-326` 的 best-effort 同样）。
2. **`_append_development_trial` 是 best-effort**：异常只写 `ledger_append_failed`，候选仍可 `development_passed`；后续 `assets.context.unrecorded_metrics`/`sealed._check_new` 会拦截封存/批准，但手工路径可能长期缺行。
3. **`policy.evaluate` K=1 缺省**：`policy.py:100-104`；新调用者漏传 K 会把门槛降到 1.96。
4. **客户端可追加 trial**：`TrialBody`（router `221-231`）+ `append_trial` 信任 `result_summary/outcome/implementation_hash`；K 只能被抬高/污染，不能降低，但“台账=真实证据”不成立。
5. **无 `UNIQUE(report_id)`**：`0011:65`；恢复/重入可能重复追加同一 report → K 虚高（推断）。
6. **方法指纹不含 `ledger.py`**：`research_method.py:17`；改 K 计数规则不会使冻结方法失效。
7. **F0 预算不减 reserved**：`f0.py:94`、`f0_agent.py:138,498`；`service.create:128-131` 才减；F0 可能先决定后失败。
8. **自动迭代用候选数预检**：`iterations.start:80-81`，不是 K。
9. **封存/批准按当前 K 重算**：`sealed.py:227-234`、`assets.py:68-77`；`trial_ids` 写入但不读；旧文档“封存 t≥1.96”不成立（推断为刻意更严，未文档化）。
