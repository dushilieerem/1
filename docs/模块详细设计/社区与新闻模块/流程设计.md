# 社区与新闻模块 流程设计

## 1. 流程说明

覆盖四条流程：社区发帖与互动、社区审核管理、资讯定时采集、资讯查询展示。

## 2. 参与模块

| 参与者 | 职责 |
|---|---|
| frontend | 社区页、资讯页、管理后台 |
| `routers/community.py` / `routers/news.py` | HTTP 入口 |
| `community_store` / `news_store` / `news_ingest` / `news_tag_dict` | 存储与采集 |
| 后台调度线程 | 周期采集 |
| 外部资讯源 | CLS/东财/巨潮/华尔街见闻/同花顺 |

## 3. 正常流程

### 流程 A：发帖与互动

```text
登录用户 POST /api/community/posts（require_user）
  → create_post：板块校验（strategy/factor/qa/hotspot/official）
  → _find_mentioned_user_ids 解析 @提及 → _insert_notification
  → INSERT posts → 返回帖子
其他用户：GET 详情（optional_user，记录 viewer_role）/ 评论 / 投票 / 收藏
作者/管理员：PUT 编辑、DELETE 删除（软删或硬删以实现为准）
```

### 流程 B：审核与运营

```text
管理员 GET /api/community/moderation（待审队列，store 校验 role=admin）
管理员 POST /api/community/posts/{id}/moderate {pinned?, status?}
        → moderate_post：status ∈ published/hidden，置顶位更新
用户 POST /api/community/reports（举报）
管理员 GET /api/community/reports → POST /api/community/reports/{id}/resolve（处理闭环）
违规帖：POST /api/community/posts/{id}/purge（彻底清除）
运营：GET /api/community/ops/summary（总量/今日新增/待处理等摘要）
```

### 流程 C：资讯定时采集

```text
进程启动 → start_news_ingest_scheduler（daemon 线程）
loop 每 NEWS_INGEST_INTERVAL_SEC（默认 900s，≤0 关闭）:
  ingest_news:
    for source in FETCHERS:            # cls / eastmoney(_research/_policy) / cninfo / wallstreetcn / 10jqka
      fetch_*（超时约 20s，每源取 ≤ NEWS_INGEST_LIMIT=12 条）
    → _hash_key(source,url,title,published_at) 去重
    → upsert_news_items 入库
    → backfill_news_tags（news_tag_dict.enrich_news_tags）
    → enrich_news_body（补正文）
    → enforce_news_retention / ensure_news_within_caps（保留与容量）
```

### 流程 D：资讯查询展示

```text
GET /api/news?category&source&q&mode&theme&symbol&industry（无鉴权）
  → news_store.list_news：SQL 过滤 + 分页
GET /api/news/{news_id} → 详情
GET /api/news/dict → 标签词典快照（dict_snapshot）
手动触发：POST /api/news/ingest（立即采集一轮）、POST /api/news/{id}/enrich（单条增强正文）
```

## 4. 时序流程（采集一轮）

```text
scheduler -> news_ingest.ingest_news：定时触发
ingest_news -> cls fetcher：HTTP（签名参数）→ 条目
ingest_news -> eastmoney fetcher：市场/研报/政策 → 条目
ingest_news -> cninfo / wallstreetcn / 10jqka：HTTP → 条目
ingest_news -> news_store：upsert（hash 去重）
ingest_news -> news_tag_dict：标签匹配
ingest_news -> news_store：retention/caps 清理
scheduler：sleep(NEWS_INGEST_INTERVAL_SEC)
```

## 5. 异常流程

| 异常 | 触发 | 处理 |
|---|---|---|
| 非管理员管理操作 | store role 校验 | `PermissionError` → 403 |
| 帖子/评论不存在 | KeyError | 404 |
| 板块/状态非法 | ValueError | 400 |
| 资讯源失败 | 网络/页面变更 | 跳过该源，日志记录，下一周期重试；连续不可用源移入 UNSUPPORTED_SOURCES 观察列表 |
| 重复资讯 | 同 hash | upsert 覆盖，不重复入库 |
| 自关注/自投票类非法操作 | store 校验 | ValueError → 400（以实现为准） |

## 6. 状态流转

```text
帖子：published ⇄ hidden（管理员 moderate；purge 为物理清除）
举报：open → resolved（resolve_report；处理动作记录以实现为准）
通知：unread → read（mark_notifications_read）
资讯：入库即生效；过期由 retention 清理
```

## 7. 并发处理

- 投票/收藏为"存在则取消、不存在则插入"式的 toggle 语义（以实现为准），并发下以唯一约束兜底。
- 计数（浏览/点赞）为直接 UPDATE，高并发允许瞬时偏差。
- 采集为单调度线程串行执行，无并发写冲突；手动 `POST /api/news/ingest` 与调度线程可能重叠（依赖 upsert 幂等）。

## 8. 幂等设计

- 资讯 upsert 以 hash 为唯一键，重复采集幂等。
- 通知已读、举报处理重复调用安全（状态置位）。
- 发帖/评论非幂等（每次新行）。

## 9. 超时和重试

| 调用 | 超时 | 重试 |
|---|---|---|
| 社区/资讯 SQL | 连接级默认 | 无自动重试 |
| 资讯源 fetch | 约 20s/源 | 下一采集周期（默认 15 分钟） |
| 手动 ingest | 同一轮采集耗时 | 用户可重复触发（幂等 upsert） |

## 10. 待确认

- 资讯端点（含手动 ingest/enrich）无鉴权，是否需要管理员限定或登录要求。
- 帖子删除是软删还是硬删；purge 与 delete 的边界。
- 举报 resolve 的处理动作集合（仅记录还是联动帖子状态）。
- 投票/收藏 toggle 的并发唯一约束具体定义。
- 社区管理员判定依赖调用方传 role 参数，是否收敛为统一依赖注入。
