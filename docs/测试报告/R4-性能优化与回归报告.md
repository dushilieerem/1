## 2. 原始问题

| 编号 | 原始现象 | 原始指标 |
| --- | --- | --- |
| PERF-R4-001 | `/api/auth/me` 100 并发高延迟与失败 | 错误率 5.27%，P95 14206.76 ms |
| PERF-R4-002 | `/api/strategy/runs` 20 并发失败 | 错误率 4.28%，P95 2177.97 ms |
| PERF-R4-003 | `/api/re/health` 通过 SVQuant 调用超时 | 15 秒超时 |

## 3. 根因分析

| 编号 | 调用链 | 根因判断 |
| --- | --- | --- |
| PERF-R4-004 | `/api/market-data/symbols` -> RE 网关 -> ResearchEngine `/api/market-data/symbols` | 网关无缓存、无 stale fallback，且对 RE 使用同步长等待；RE 冷启动或不可用时会占用后端同步线程，稳定性流量被放大为超时 |
| PERF-R4-003 | `/api/re/health` -> RE 网关 -> ResearchEngine `/api/health` | RE health 端点本身可能慢或不可用；原实现每次请求都同步等待远程 health，没有短 TTL 缓存或本地可服务性降级 |
| PERF-R4-001 | `/api/auth/me` -> JWT 解码 -> DB 查询用户 | 认证逻辑本身轻量；高并发失败更像被同步路由线程、数据库连接创建和外部慢请求共同拖慢 |
| PERF-R4-002 | `/api/strategy/runs` -> 用户鉴权 -> `strategy_runs` 查询 | SQL 基线不慢；目标回归中出现 500，暴露出高并发下数据库连接/请求资源管理不稳 |

数据库专项补采结果显示 `strategy_runs` 查询执行耗时约 0.064 ms，未发现慢查询、长事务或连接泄漏。因此本轮优先处理网关阻塞、连接复用和错误分类。

## 4. 修改内容

| 文件 | 修改内容 |
| --- | --- |
| `backend/app/routers/re_gateway.py` | 为 market symbols/indices 增加进程内缓存、stale fallback、本地应急 symbols/indices；为 RE health 增加短超时、本地目录镜像降级和短 TTL 缓存 |
| `backend/services/core/lan_http.py` | 将上游 timeout、connection error 分类为结构化 504/502 响应 |
| `backend/app/main.py` | 启动时配置 FastAPI/AnyIO 同步路由线程额度，降低慢同步请求对轻量接口的连带影响 |
| `backend/services/core/db.py` | 增加进程内 PostgreSQL 连接复用池，减少高并发下频繁建连开销 |
| `backend/tests/performance/performance_baseline.py` | 增加状态码分布与错误类型分类，不改变测试标准 |
| `backend/tests/performance/r4_fix_regression.py` | 新增 R4 性能修复目标回归脚本，覆盖四个 R4 性能缺陷 |

## 5. 性能优化方案

| 范围 | 优化策略 |
| --- | --- |
| Market symbols | 首次请求尝试 RE，失败后返回本地 fallback，并在 stale TTL 内复用 fallback，避免稳定性流量持续阻塞 RE |
| RE health | 远程 health 短超时；失败时用本地 `re_factor_catalog_snapshot` 作为降级可服务性证据 |
| HTTP 转发 | 明确区分 `timeout`、`connection_error`、`server_error`、`client_error` |
| 同步路由 | 提升同步路由线程额度，降低外部慢调用对 `/api/auth/me` 等轻量接口影响 |
| 数据库访问 | 引入连接复用池，降低并发场景下反复创建 PostgreSQL 连接的开销 |
