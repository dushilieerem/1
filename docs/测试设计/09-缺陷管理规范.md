# 09 缺陷管理规范

> 适用范围：本项目全部测试活动（contract 脚本、pytest、手工执行、UAT）。承接 `docs/测试设计/测试设计.md` v2.0 的缺陷分级（P0–P3）并细化；现有测试文档中 P0–P3 定义与本规范冲突时以本规范为准。
> 状态：规范即生效；当前无缺陷登记（本轮未执行测试）。

## 1. Severity（严重级）——由缺陷本身决定

| 级别 | 定义 | 本项目示例 |
|---|---|---|
| Blocker | 系统不可用/数据损毁/安全底线失守，无法继续测试 | 生产可开启 DEV_SKIP_AUTH 且无拦截；生产库被测试写入；登录功能整体失效 |
| Critical | 核心功能失效或越权/数据泄漏 | IDOR 读取他人策略回测结果；JWT 伪造被接受；XSS 可执行；回测结果被伪造成功 |
| Major | 主要功能部分失效，有绕过路径 | RE 不可达时返回伪造数据；镜像 sync 误清空；额度可被并发超卖 |
| Minor | 次要功能/文案/边界体验问题 | 分页越界报 500 而非 400；错误文案不可读；bump 计数口径偏差 |
| Trivial | 外观/提示瑕疵，无功能影响 | 错别字、样式错位 |

## 2. Priority（修复优先级）——由排期决策决定

| 级别 | 定义 |
|---|---|
| P0 | 当前迭代必须修复，阻塞发布 |
| P1 | 下一迭代修复 |
| P2 | 排期内修复 |
| P3 | 观察/低成本低风险时顺手修复 |

**Severity ≠ Priority**：Critical 缺陷若属"现网无此暴露面"（如仅 DEV 暴露的 KH 匿名管理，且生产将强制 `KH_REQUIRE_AUTH=1`）可定为 P1；Minor 缺陷若一行即修且发布在即可定 P0。每条缺陷两个字段独立填写并给出理由。

## 3. 用例执行状态语义（唯一合法集合）

| 状态 | 含义 | 约束 |
|---|---|---|
| NOT RUN | 已设计未执行 | 初始状态；未执行用例**禁止标 PASS** |
| PASS | 真实执行且结果符合预期 | 必须有 evidence 引用（RUN_ID + 截图/输出） |
| FAIL | 执行了且不符合预期 | 必须关联 Bug ID（§5 模板） |
| BLOCKED | 无法执行（环境/依赖/上游阻塞） | 必须注明阻塞项（对应 02-测试计划 B-1..B-5） |
| NOT APPLICABLE | 不适用于当前实现/规划中能力 | 必须注明理由（如 201/409 未使用、规划中能力） |
| PLANNED | 已规划待建（仅用于工具/脚本类，如 RE 桩 fixture） | 不用于功能用例 |

## 4. 缺陷生命周期

`New → Confirmed → In Progress → Resolved → Closed`，旁路：`Rejected`（非缺陷/无法复现）、`Deferred`（延后，须给出版本号）。

本轮无缺陷管理系统：缺陷登记采用 `docs/测试设计/evidence/<RUN_ID>/bugs.md` 表格（模板见 §5），后续若引入 issue 跟踪，按 Bug ID 迁移。

## 5. 缺陷报告模板（bugs.md 行格式 + 详单格式）

**Bug ID 规则**：`BUG-<模块码>-<三位序号>`，模块码同用例前缀（AUTH/FACTOR/STRATEGY/MKT/COMMUNITY/NEWS/KH/AI/ADMIN/RE/COMMON/DB/SEC/PERF）。

```
### BUG-<模块>-<NNN> <一句话标题>
- Severity: Blocker|Critical|Major|Minor|Trivial ｜ Priority: P0|P1|P2|P3
- 模块: M# <模块名> ｜ Req: REQ-XXX-NNN ｜ Case: TC-XXX-NNN
- 环境/RUN_ID: <RUN_ID>（DEV/TEST） ｜ 复现率: 必现|偶现(<n>/<m>)
- 前置条件: ...
- 复现步骤: 1) ... 2) ...
- 预期结果: ...（引用需求/文档依据）
- 实际结果: ...
- 证据: evidence/<RUN_ID>/... （截图/请求响应/日志片段；严禁包含密钥与生产数据）
- 初步定位（可选）: <文件:行 或 推测>
- 备注: ...
```

## 6. 缺陷与文档联动

1. 新缺陷若暴露**设计文档与代码不一致**，同步补记 01-测试策略 §DESIGN-CODE-MISMATCH（新编号顺延）。
2. 缺陷修复后，回归时必须重跑原用例 + 关联回归集（10-测试执行计划 §3）。
3. 严重级 Blocker/Critical 的修复需在 evidence 中保留修复前后对比。
4. 每个 RUN 结束输出缺陷汇总：按 Severity × Priority 矩阵计数、按模块分布、遗留风险清单。

## 7. 防止状态失真（本轮既定纪律）

- 报告与文档中**不得出现未经执行的 PASS**；"看起来应该能过"不是 PASS。
- 契约脚本全绿（`ALL CONTRACTS OK`）只代表脚本覆盖的 ~20 端点契约通过，**不得**在报告中等同于"测试通过"；re-catalog 允许 502 的豁免必须在报告中显式注明。
- 任何"达标"结论仅性能用例真实执行并经责任边界拆解（07-性能测试）后允许给出。
