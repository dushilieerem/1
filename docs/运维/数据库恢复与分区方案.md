# 数据库恢复与分区方案（PITR + 大表分区）

> 现状盘点于 2026-11-09：PostgreSQL 16.15 单实例；`svquant` 库 21 GB，数据目录 38.6 GB。
> 备份只能恢复到最近一次 `pg_dump` 的时点，**没有时间点恢复**；`md_daily_bar` 5.6 GB / 3137 万行未分区。

## 1. 现状与缺口

| 项 | 现状 | 风险 |
|---|---|---|
| WAL 归档 | `archive_mode=off` | 无法恢复到任意时间点，误删/误改只能回到昨天 |
| 备份 | `deploy/backups/` 手工 + 发布时各一份，保留 7 份 | 每天 03:10 的定时备份 2026-11-09 才修复，尚未经历一轮验证 |
| 备份位置 | `/home`（365G，与数据盘 `/data` 分开） | 同机同机房，机器级故障会一起丢 |
| 大表 | `md_daily_bar` 5.6 GB、`md_valuation_daily` 2.2 GB，无分区 | VACUUM/建索引/按日期查询随数据增长变慢 |
| 连接 | `max_connections=100`，后端池上限 25 | 目前 35 连接，余量够 |

目标（按优先级）：

1. 能恢复到「任意时间点」（PITR），RPO ≤ 5 分钟；
2. 备份离开本机（异地/独立盘），保留策略明确；
3. 两张 MD 大表按月分区，历史分区可归档搬迁；
4. 全流程可演练、有监控、有回滚。

## 2. PITR（WAL 归档 + 定期全备）

### 2.1 配置

```conf
wal_level = replica          # 已满足
archive_mode = on
archive_command = 'test ! -f /backup/wal/%f && cp %p /backup/wal/%f'
archive_timeout = 300        # 最多 5 分钟强制切一个 WAL，控制 RPO
wal_keep_size = 1GB
```

- `/backup` 挂独立盘（当前 `/home` 可用 245G，或外挂盘），**不要与 `/data` 同盘**。
- `archive_command` 必须幂等且返回非 0 时 PostgreSQL 会保留 WAL 重试；配合监控告警。
- 需要 `docker exec svquant-db-1 psql -c "ALTER SYSTEM SET ..."` + 重启 db 容器（约 10 秒停机），建议放在低峰窗口。

### 2.2 备份节奏

| 类型 | 频率 | 保留 | 说明 |
|---|---|---|---|
| 全量 `pg_dump` | 每日 03:10（已有） | 7 天 | 逻辑备份，用于快速回滚单表/单库 |
| 基础备份 `pg_basebackup` | 每周日 04:00 | 4 周 | PITR 的起点 |
| WAL 归档 | 持续 | 14 天 | 与基础备份配套 |
| 异地副本 | 每日 rsync | 7 天 | `/home` → 备份机/对象存储 |

保留策略写进脚本：`find /backup/wal -mtime +14 -delete`，基础备份按周清理。

### 2.3 恢复流程（演练用）

```bash
# 1) 停业务写入（或起一个独立实例恢复到新端口）
docker run -d --name pg-restore -e POSTGRES_PASSWORD=... -p 55440:5432 postgres:16-alpine
# 2) 解基础备份
gunzip -c base.tar.gz | docker exec -i pg-restore tar xf - -C /var/lib/postgresql/data
# 3) 写 recovery 配置到 postgresql.auto.conf
restore_command = 'cp /backup/wal/%f %p'
recovery_target_time = '2026-11-10 14:00:00+08'
# 4) 启动，确认 recovery 完成后 promote，比对数据
```

演练频率：每季度一次，把「恢复到昨天 14:00」跑通并记录耗时。

### 2.4 监控

- `pg_stat_archiver.failed_count` 增长 → 告警（`scripts/ops/check_alerts.py` 增加一项）；
- 最新归档时间距今 > 15 分钟 → 告警；
- 备份文件 `gzip -t` 校验失败 → 告警（`backup-db.sh` 已有校验，失败即退出）。

## 3. 大表分区（`md_daily_bar` / `md_valuation_daily`）

### 3.1 目标结构

按 `trade_date` 月度 RANGE 分区：

```sql
CREATE TABLE md_daily_bar_p (
  symbol text NOT NULL,
  trade_date date NOT NULL,
  open numeric, high numeric, low numeric, close numeric,
  volume bigint, amount numeric,
  PRIMARY KEY (symbol, trade_date)
) PARTITION BY RANGE (trade_date);

CREATE TABLE md_daily_bar_2026m11 PARTITION OF md_daily_bar_p
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
-- 历史月份按月补建，最早到 2015-01
```

要点：

- **主键必须包含分区键**（`symbol, trade_date`），现有唯一索引若不含 `trade_date` 需要调整；
- 提前建未来 3 个月的分区，用定时任务每月补建（建议放在 `sync_data_view` 之后）；
- 查询侧不用改：现有 SQL 都带 `trade_date` 条件时能命中分区裁剪；不带日期的全表聚合会扫所有分区，速度与现在相当。

### 3.2 迁移步骤（可回滚）

数据量 3137 万行，直接 `INSERT INTO ... SELECT` 约 10~20 分钟，采用「影子表 + 原子切换」：

1. 业务低峰建 `md_daily_bar_p` 及全部分区；
2. `INSERT INTO md_daily_bar_p SELECT * FROM md_daily_bar`（分批，按 `trade_date` 月份循环，避免长事务撑大 WAL）；
3. 校验行数、`min/max(trade_date)`、抽样比对 close/volume；
4. 一个事务内：`ALTER TABLE md_daily_bar RENAME TO md_daily_bar_old; ALTER TABLE md_daily_bar_p RENAME TO md_daily_bar;`
5. 观察 1~2 天，确认同步任务/查询正常后 `DROP TABLE md_daily_bar_old`（可先 rename 保留一周）。

回滚：切换后出问题，同一事务反向 rename 即可（旧表仍在），代价是切换期间写入需要重放。

### 3.3 历史归档

`ALTER TABLE md_daily_bar DETACH PARTITION md_daily_bar_2020m01;` 然后 `pg_dump` 或直接 `COPY` 到冷存储，释放热库空间。建议保留最近 3 年在线。

## 4. 执行顺序与窗口

| 步骤 | 预计耗时 | 停机 | 说明 |
|---|---|---|---|
| ① 开启 WAL 归档 | 10 分钟 | db 重启 ~10s | 先做，收益最大 |
| ② 加归档监控与异地 rsync | 30 分钟 | 无 | 脚本 + 定时任务 |
| ③ 每日备份验证一轮 | 次日 | 无 | 看 `db-backup.date` 与 `gzip -t` |
| ④ 迁移 `md_daily_bar` 分区 | 1~2 小时 | 切换瞬间秒级 | 低峰窗口 |
| ⑤ 迁移 `md_valuation_daily` 分区 | 30~60 分钟 | 同上 | 与 ④ 同一窗口 |
| ⑥ 恢复演练 | 1 小时 | 无（独立实例） | 每季度 |

## 5. 风险与回滚

- WAL 归档失败会持续堆积 WAL（`max_wal_size` 1024 MB 后开始强制检查点），磁盘会被吃满——必须在此之前告警；回退方式是 `archive_mode=off` + 重启。
- 分区迁移期间双写风险：迁移脚本只读旧表、写新表，切换瞬间窗口内若有写入会丢，建议放在同步任务完成后、无业务写入的时段，并在切换后立即补一次增量同步。
- 所有步骤先在 `svquant_test` 完整走一遍（含恢复演练），再上生产。

## 6. 不在本方案内

- 主从/读写分离、逻辑复制；
- 跨机房容灾；
- `md_status_daily` / `md_risk_daily` 等其他表的归档（数据侧确认后再定）。
