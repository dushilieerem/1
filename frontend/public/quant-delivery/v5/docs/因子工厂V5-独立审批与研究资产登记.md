# 因子工厂 V5 · 独立审批与研究资产登记补充

2026-11-09 · CR-095 · 产品经理 Codex · dev-zxd
本补充落实CR-083“审批入库”已有要求，修正现有实现仅写研究意见/未准入留档的断点，不降低078/083的统计、查重、封存和权限规则，不重画因子首页。

## 1. 明确区分
- research_supported 是既有研究反馈，不自动解释为批准或登记。
- research_only 未准入留档保留原意，不批量迁移成“已入库”。
- 新决定 approve_research_and_register 明确表示独立复核人批准本冻结成果供机构内部后续研究，并完成研究资产登记；不授予实盘或投资指令权限。
- 新发现需正式、完整的新颖性/去重证据；受控小参考诊断不能伪装正式全库验证。
- 复现任务允许与目标已有因子高度相关，不按新发现去重门槛否决，但必须有目标身份/版本及真实研发、独立验证证据。它登记复现验证记录并关联原因子，不重复创造“新发现因子”。仍按QA-16在送审前补齐真实对照结果、范围及最相关项；允许先封存不等于允许缺对照证据直接批准。

## 2. 独立复核流程
1. 研究端提交符合准入条件的固定候选；封存失败可单独进入复盘，不能混入待批准。
2. 有独立复核权限者领取事项；作者不能领取自己的批准事项，已由他人领取时不能抢占。
3. 查看固定因子实现、研发和封存报告、全量试验/K、查重范围、数据与政策版本、限制。
4. 独立分析意见作为意见返回，不用该响应覆盖整个候选对象。
5. 批准研究用途并登记 / 退回补证 / 驳回。无证据、范围不全、错误或在途状态禁止批准。
6. 成功后显示登记ID、因子版本、报告、分类/标签和用途，在因子库可检索；失败保持原记录，不显示已入库。

## 3. 最小存储与事务契约
MVP可复用现有quant_factor_candidates.archive JSON，无需为了本批单独建表；未来迁表须有版本化迁移。不依赖作者个人user_library充当机构公共库。
- 稳定资产标识与候选一一对应，同一批准请求重放返回同一登记结果。
- 同一PG事务与候选行锁完成审批、不可变资产快照及审计事件；登记失败回滚批准，禁止“批准成功但资产不存在”。
- 登记至少含org_id、candidate_id、snapshot_hash、固定实现/说明、数据/方法/政策版本、研发和封存/查重报告引用、审批时实际K及阈值、分类标签及来源、审批人/时间、research_only。
- 最新K/门槛与在途修改检查须与批准写入协调；禁止一边继续试验、一边用过期门槛批准。沿用已有计划冻结规则，不能在批准后覆写快照。
- 不覆盖旧review历史；重复提交幂等，不可改写已决定版本。原研究反馈不升级。新审批事项有明确purpose；历史反馈后申请合格资产审批要新建审批记录/事件并保存旧反馈，不覆盖历史review。
- 发布后停用/撤回应另有审计事件，不能删除既有研究引用；本批不新增自动撤回系统。

## 4. 批准时后端必须核验
独立复核权限、机构、作者不同、已领取、事项仍待处理、固定hash/版本一致、无在途修改、研发硬门槛及当前K校正、封存通过、完整所需证据。
新发现另核查重complete/pass与正式对照范围；小参考/部分覆盖/未知结果拒绝。复现核验与源因子对应，不伪造新颖性通过。
seal_failed_review不可批准。模型意见不能覆盖硬条件，前端按钮禁用不能代替后端校验。

## 5. 资产可见与复用
- 新增机构资产列表/详情采用明确权限及字段白名单，只返回获批准的登记快照与授权证据。
- 不因机构资产可读而放开作者私有project、研究对话、事件全文或全部candidate接口。
- 机构隔离在SQL/服务层执行；越权ID不可绕过，测试覆盖不同org和不同权限。
- 后续研究复用读取冻结快照并保存来源资产ID、版本，不继承已通过状态；新修改形成新版本与新验证。
- 因子库展示业务分类/真实标签、版本和批准用途；旧未准入留档不得冒充正式研究资产。
- 不覆写共享RE内置/官方因子、个人库或社区发布内容。

## 6. 验收与真实计算边界
- 先隔离验证：自己批准/跨机构/未领取/封存失败/小参考/证据错配/过期K拒绝；重复批准同ID；事务失败不残留半批准；独立意见不破坏候选。
- 真实研究先给资源方案，沿用内存事件后单任务、并发1、≤3个月、小参考诊断及RSS记录，不扩大模型预算，不重跑用户T10/T11。
- 若只有诊断证据，验证结束于未达标/等待/停止归档，不人为改状态送入正式批准。
- “真实新发现合格→独立批准→研究资产入库”仍需单独真实证据，未做到据实记待验。不能以原型、替身用例、复现已有因子或诊断通过代替。
- 业务数据结构/接口改动完成后通过机构专用联络会话向SVQuant业务汇报，不把联络会话变回代码开发者。

## 7. 审批界面增量与原型关系

继续采用 factor-factory.html 的待审批主卡、证据入口、右侧独立审查说明、底部决定操作结构。本补充允许以下由真实后端约束产生的增量；不是另起一页、把所有证据全部平铺或重画流程。
- 领取状态放主卡标题下的状态行：未领取 / 我在复核 / 已由其他复核人领取。未领取的独立复核人显示“领取复核”；领取前决定操作不可用。研究员只看材料，不能出现批准入口。
- 三个决定保留原型位置：“批准研究用途并入库”“退回补证”“驳回”。批准按钮仅在完整正式证据及权限满足时可用；缺口在相邻位置以业务语言说明。
- 点击决定沿用原型弹窗。批准弹窗：因子名称（最多100字）、分类（与目录现有真实分类一致）、标签（选填，不生成全库标签）、复核依据、已核对冻结材料确认。提交后等待服务端结果；不可点击即先显示成功。
- 旧反馈事项只显示“认可研究依据”等原意义的操作，不复用入库按钮；封存失败事项明确“失败复盘”。复现审批显示“登记复现验证记录”，不得显示“发现新因子”。
- AI复核意见留在证据/审查区，使用已领取权限；生成结果仅更新意见，不替换当前候选、不自动作批准决定。
- 批准后显示登记成功、业务名称、研究用途、版本与“在因子库查看”。内部完整ID仅在详细记录中可复制，不作为大标题或用户唯一识别信息。
- 新资产进入现有因子库及分类/搜索；复现验证记录归在原因子详情的验证记录中。不能新增按“SVQuant已有/平台内置/本产品”分裂的来源导航。

原型当前表达的是批准交互和示例分类；领取状态与严格的后端准入条件以本补充为批准的明确增量。实现需提供相同候选状态的原型/正式对照，差异仅限上述功能所必需的状态和表单，不以新需求掩盖其他布局漂移。
