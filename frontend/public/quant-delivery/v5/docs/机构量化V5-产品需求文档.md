## 2. 产品范围与主链路

面向机构内部量化投研。研究员可自主使用真实工具，研究系统也可在授权、预算和数据范围内自主推进。需要复核、授权、模拟部署和风险恢复时，转入人工待办。当前研发与回测使用真实数据，组合运行采用模拟成交，前端全程明确所处环境。

**主链路**。数据发布视图 → 因子假设和试验证据 → 可用因子资产 → 策略配方和证据 → 策略准入 → 模拟组合审批、运行 → 风险处置、归因 → 新的改进任务。

各模块从已有、可用的资产独立发起工作。策略研究可选机构允许的已有因子，组合经理可选已有模拟准入策略。因子正在挖掘新候选时，其他模块可继续使用库内相应版本。

**分期**。M1 先收口因子，M2 验收策略，M3 开展组合及模拟执行，M4 验收运行与风险，M5 交付数据资源与公共入口，M6 完成联测。数据和公共入口可穿插。评测编排、更多模板、复杂归因等按路线图排期。未达到当前里程碑的能力在页面上按真实状态展示。

## 3. 角色与共用规则

| 角色 | 可做的操作 |
| --- | --- |
| 研究员 | 按授权看课题、使用库内资产、接手或交回研究分支、使用人工工具和助手，提交本人的研究候选或数据需求。 |
| 独立复核人 | 打开分配给自己的因子或策略候选，核对证据，记录批准研究用途、模拟准入、退回或拒绝。本人提交的候选禁止自审。组合审批按阶段授权。 |
| 研究负责人 | 管理本机构研究授权、计划版本、试验与模型预算，批准范围扩展，暂停和恢复授权范围内的自动研究。 |
| 投资负责人 | 建立组合草稿、检查风险、提交版本、管理已批准模拟组合。方案由具审批权的其他成员决定。 |
| 风控负责人 | 检查事件、确认收到、处置、提交复测证据并按权限恢复模拟调仓。风险规则发布由授权管理员执行。 |
| 数据维护职责 | 研究端查看发布视图、数据质量与使用关系。采集、清洗和发布归数据平台维护方。机构成员从数据资源提交需求并追踪结果。 |
| Agent 管理职责 | 授权管理员查看方法和用量，管理自动能力开关。授权审批、资产准入和风险解除由具备相应权限的人工角色决定。 |

开发沿用现有机构账号、成员和产品权限。岗位职责按现有角色映射，具体授权需写入实施计划。服务端校验机构范围、对象访问权、操作权、版本与自审限制。页面同步显示权限和理由。研究、回测、封存、复核、审批等记录绑定同一机构、对象版本、操作者和时间。

**统一界面**。侧栏按原型保留「工作空间」「业务模块」「协作与管理」，原型页面入口和 V5 文档入口常驻。页头显示所在模块、当前身份与研究或模拟环境。按原型核对中英文、1366 和 1024 宽度、键盘可操作性。加载、空列表、未接入、无权限、任务失败分开提示。报告或记录缺失时明确展示当前能取得的证据。

**资产和状态**。数据视图、假设、表达式、策略配方、组合、授权与政策均按版本引用。重新试验和新版本追加证据。报告历史数据及复核结论仍可追溯。用真实状态显示运行、等待数据/授权、暂停、失败、复核等，区分对象生命周期与后台任务是否正在计算。一次性封存和后台调度的重复请求按同一业务键识别，重试保留日志。

## 6. 因子工厂

当前入口 /quant/factor，对应 [factor-factory.html](../factor-factory.html)。本节已按 CR-083 v1.2 整体同步，旧 factor.html、五个并列页签与以研究树为首屏主体的表达不再是开发依据。统计口径、内部方法、预算、封存和入库权限继续按因子详规与有效补充执行。

| 主入口 | 当前需求 |
| --- | --- |
| 挖掘任务 | 左侧任务列表支持搜索、状态筛选；选中任务后显示研究准备→因子研发→独立验证→审批入库。主区展示当前环节的真实产物与操作，右侧显示正在做什么、最近事件和待人处理项。研究历程与全部试验默认折叠，H1/Ha/Hb等真实稳定编号、父子虚线、各轮报告继续保留。 |
| 待审批 | 呈现当前权限内的候选队列、冻结证据、全部相关试验、独立意见及决定。通过硬门槛且材料齐全才可批准；仅独立复核人决定研究用途入库，提交者不能自审。 |
| 因子库 | 统一目录；按真实业务多级分类、关键词、可用状态及具备来源的因子级标签查找。接入来源仅在详情显示，不作为“SVQuant已有/平台内置”等主导航。无因子级标签显示未标注，不能使用全库标签数组冒充。指标展示真实口径与局限。 |

人工研究是当前任务/分支的操作，进入已有工具页；能力与评测从Agent管理或更多入口访问。二者不是本模块并列主页签，原深链与功能继续可用。人工与Agent共用工具、版本、台账、门槛和预算，不能另建未计账路径。

**创建与启动**。入口“启动挖掘”，默认新因子挖掘，不要求先选旧因子。显式选择改进/复现时使用相应参考资产。确认所示授权范围与预算后，“创建并启动”一次得到同一任务与运行标识；“保存草稿”不启动。服务端执行，关闭浏览器不停止；创建、启动响应丢失后的重试须复用身份，不能重复建任务或扣费。机构预算默认来自已生效政策，样例8次和诊断1次均不直接成为产品默认。

**真实阶段与研究控制**。当前环节、执行状态、最近事件和产物由真实运行记录提供；用户选择查看哪一环节不改变实际运行，也不因状态刷新被强制切走。研发环节内仍可修订、分支、检验、停止；四环节不是内部单向流水线。草稿、排队、运行、等待、系统异常、未达标结束、待审批、已入库应正确区分。人工接手与授权有真实事件和权限，界面不显示AC/F0等开发编号。

**本轮回验**。按 CR-083 UX-01～15 与本文§12.3逐屏、逐状态对照。因子详规中有效的真实模型/RE、人工往返、研究树、冻结证据与独立审批用例继续执行；数据和服务缺口如实记录，不能因画面符合原型就宣布真实闭环完成。

## 12. 验收交付

1. 开工在 `开发进度-V5.md` 记录采用的原型源码版本、PRD、模块规格、功能范围、后端复用、依赖与计划。涉及现有服务、表或权限的变化按公司流程报备。
2. 每屏列「原型区块或动作 → 开发路由 → 接入数据与权限 → 已实现／待接入／获批差异」。提交 1366 同屏对照图、1024 可操作性和真实流程证据。业务编号、控件状态、跳转、空态、错误、刷新和跨页对象身份与视觉一起验收。
3. M6 使用真实数据完成路线图 §10。因子与策略的失败分支保留真实结论。组合与风险流程在模拟环境走通，驾驶舱、审查和 Agent 指标与源记录交叉核对。
4. 产品经理在开发环境按身份实测，通过后记验收结果。研发测试、真实模型与行情、浏览器操作证据分别登记。PR 由 mentor 审批合并。

### 12.1 产品变更与签收

按已经确认的基线发现实现偏差，登记 QA 并按现有原型和规格回验。产品要改交互、增加功能或改变业务规则时，先登记一个变更编号，确定受影响的页面、角色、状态、数据和上下游，再变更这组交付。

| 步骤 | 负责人及完成条件 |
| --- | --- |
| 1. 说明改什么 | 产品经理写明原因、受影响页面或功能、改动前后、权限与依赖。涉及已确认的范围、预算或审批权时，由对应决定人确认。 |
| 2. 更新同一版 | 产品经理修改受影响的原型源码、PRD 或模块详规和验收用例。涉及可见变化时同时交付原型和规则。仅调整内部能力时交付对应规格与测试，明确引用的原型版本。 |
| 3. 发一份交接单 | 交接单列原型和规格路径、提交版本、具体条款、涉及页面、验收步骤和被替代的条款。旧版本归档。两份资料有冲突时先由产品确认。 |
| 4. 开发签收 | 开发在共享协调目录回执实际采用的原型和 PRD 版本、影响范围和待确认项。确认后更新该变更的实施计划。尚有冲突的页面按当前已签收基线继续维护，等口径确定后切换。 |
| 5. 实机回验 | 开发提交原型和运行页同屏证据、真实操作与角色测试。产品经理对照两份底稿实操，给出通过、待修复或批准差异。仅相符的项目进入验收完成。 |

交接记录至少包含「编号／原因／旧行为 → 新行为／受影响页面及角色／原型版本／需求条款／验收步骤／开发签收／实机结果」。局部修改只更新相关页面、条款和用例。示例是调整「新建课题」入口时，同步改原型中的入口和表单、规格里的建题权限与状态，再验证不同角色、真实创建及权限不足的场景。

### 12.2 文档发布校验

四份仓库 Markdown 是源文档。开发环境的浏览版本从源文档同步生成，允许转换原型相对链接以适配预览路径。每次交付核对四份预览正文与源文档一致、原型与规格的链接可打开、页面入口显示同一版本。源文档、浏览版本与交接记录在一个发布批次内更新。验收以仓库版本和可访问的运行页为证据。


### 12.3 原型到正式页面的执行门槛（R2，2026-11-09）

此节落实已约定的原型还原，不新增产品功能或要求用户逐项批准。PM负责唯一基线、设计冲突和验收，开发负责实现、自测、截图和差异说明。

1. **同一套有效底稿**。交接记录固定原型HTML/CSS/JS及需求的commit/哈希。变更时PM同时修改受影响正文，不能只在顶部贴覆盖声明却保留相反的现行页面要求。历史文档显式标历史。原型、规则冲突由PM澄清；开发不自行选一个版本拼接。
2. **直接复用页面结构**。将原型DOM结构、CSS/设计变量、区块和交互拆为正式组件；替换场景状态、模拟动作、数据绑定和权限校验，移除原型专用场景/身份开关。保持信息层级、相对位置、主次操作和操作路径；工程拆组件、类型或内部方法可自行优化，不借接API重画界面。
3. **先验一个完整代表页面**。首次采用新模块布局，先交一个已接实际组件的完整页面，附1366宽同状态对照及1024检查，PM核对后再把该布局扩展至同类页面。本轮代表页面是因子挖掘任务详情：任务列表、四环节产物区、右侧工作、研究历程一起对照。等待布局确认期间继续不依赖该布局决定的后端、接口和测试；已有确定的设计及090明确缺陷不需等待再次签收，不变成逐按钮请示。
4. **自动检查与人工比对结合**。用正式组件的稳定测试场景检查主导航、四环节名称、关键动作、折叠行为、状态/权限以及刷新不抢焦点；截图比较固定视口、身份和业务状态，时间/任务ID等动态值可合理屏蔽，不能屏蔽关键内容、按钮或错误。隔离视觉场景明确标注，不能冒充真实研究。已有浏览器工具可截图，不要求额外全量计算。基准截图不随实现自动更新，需有已批准设计变更。
5. **两类验收都要通过**。界面验收核布局、信息层级、样式、状态与操作；功能验收核真实输入输出、权限、持久化和事件。构建/单测通过不能代替浏览器界面验收；截图好看也不能代替功能。若缺浏览器证据，记“视觉待验”，不能记“页面完成”。
6. **偏差有入口、只有影响项等待**。需改变布局、删区块、改文案含义或操作顺序时，发“原设计—发现的问题—建议—影响范围”及截图，由PM决定并同步原型/规格。普通实现选择无须请示；依既有设计修Bug直接做。未批准的偏差在交付中列待修，不能用“已实现”覆盖。
7. **交付与状态**。每批只补受影响页/状态的证据；开发自测→待PM验收→PM通过→按公司PR审批/发布，分别记录。完成一个合格批次后继续已批准任务，不等用户转发或反复催促；具体阻塞写明、其他独立工作继续。PM发现偏差须下发可核验问题并复验，不以签收替代监督。

每屏交付沿用下表，不另起一套文档系统：

| 原型区块/状态 | 正式路由与组件 | 真实数据/权限来源 | 同视口对照图与交互证据 | 差异及批准编号 | 开发自测 / PM结论 |
| --- | --- | --- | --- | --- | --- |
| 挖掘任务详情：列表/四环节/工作栏/折叠树 | 记录实际页面及组件 | 记录任务阶段、产物与事件来源 | 1366同状态对照、1024可操作性 | 无差异或已批准变更；未批准为待修 | 分别填写，不预填通过 |
| 草稿/准备/研发/验证/待审批/已入库/未达标/系统异常 | 同一页面的实际状态 | 不能以次数猜阶段、不能用全局数冒充单任务 | 可先做隔离组件场景，再按实际证据核功能 | 缺真实证据的状态列待验 | 区分模拟、实际数据和PM实测 |
